### 1.2 需要**订正**的 8 处

#### 订正 1 ｜ `W0-2` 说"删 **4 处**未使用绑定"，实为 **3 处**

父文档 `W0-2` 写"删 4 处未使用绑定"，却只列 3 个位置。实测 `npm run lint` 的 3 条 warning 恰好对应 3 个绑定：
`scripts/check-file-size.mjs:120` 的 `rows`、`scripts/check-licenses.mjs:66` 与 `:229` 的 `file`（均 `no-unused-vars`）。
**处置**：按 3 处执行；`todo.md:64/296` 的 `I40` 条目写的就是"3 条 / 三个"，以它为准。

#### 订正 2 ｜ `W0-15` 把「7 warn → 0」当作**阶段 1 的量化验收** —— 这条验收是**空心的** ⚠️

`.dependency-cruiser.cjs:44-56` 的规则是：

```
from: { path: '^apps/web/src/components/' }
to:   { path: '^apps/web/src/hooks/' }
```

而阶段 1 要做的恰恰是把 6 个面板搬进 `widgets/**`、把 `hooks/useWorkbench.ts` 搬成 `app/model/workbench.ts`
（拆分计划书 §14.2 ③⑤）。**规则两端的路径同时失效 → 规则匹配不到任何模块 → 自然报 0 条**，
但面板依赖的仍是同一个"上帝钩子"，耦合一点没少。

配置自己的注释（`.dependency-cruiser.cjs:38-42`）写得很清楚：
> 它的价值在于**阶段 4 改完后**这条会自然变空，届时转 error 即为门禁。

即：**按设计，"自然变空"的时点是阶段 4，不是阶段 1。**

**处置**：
1. "7 → 0"**不能单独作为阶段 1 的验收**。必须配 `grep -rn "useWorkbench" apps/web/src` 的**计数**（阶段 1 后应仍为 8 处：6 个面板 + 其余引用）—— 这才是"耦合还在"的证据。
2. 搬迁的**同一次提交**里必须把规则的 `from`/`to` 改写成新路径，否则转 error 得到的是一个**匹配不到任何模块的门禁**（与 `I24` 恒真断言、`I40`"告警常态非零"属同一类教训：判据失去分辨力）。
   实测基线：`grep -rn "useWorkbench" apps/web/src` 现为 **11 处**（`App.tsx` 2 ＋ 6 个面板 8 ＋ 钩子自身 1）。
   **阶段 1 只搬路径、不减耦合 → 这个数仍应是 11**；阶段 4 的目标才是 **0**。两次验收各用各的判据。
3. 正确的分期是：阶段 1 改写规则路径（仍是 warn）→ 阶段 4 删门面后改成 from `widgets/` to `app/model/` 且清零 → **那时**转 error。

#### 订正 3 ｜ `§五 #4`（三处清零后才可转阻断）与 `W0-15`（阶段 1 就转阻断）**互相矛盾**

`§五 #4` 要求转阻断必须在**三处清零之后**：`lint` 3 warning + `lint:boundaries` 7 warn + `file-size` 5 个超限文件。
但"任一文件 ≤300 行"是**阶段 4** 的目标（拆分计划书 §14.5 验收 ④）。按 `#4` 执行，转阻断最早只能到阶段 4 之后；
按 `W0-15` 执行，阶段 1 一开就把团队挡在 5 个超限文件上。

**处置**：二选一，**建议采纳拆分计划书的原设计**（也是 `.dependency-cruiser.cjs:38-42` 的原意）：**逐条转**，不搞一次性总开关。
`§五 #4` 应改写为"**每条规则在它自己清零之后**转阻断"，而不是等三处全清。

#### 订正 4 ｜ `§九`「上传包清单与 `main` 只差检查清单文档」—— **文件清单成立、内容不成立** ⚠️

#### 订正 6 ｜ `W0-6`（`I39` 根治：重生成锁文件）放在"今天就能开"层，在本机是**高危操作** ⚠️

实测：`package-lock.json` 全表 `@rollup/rollup-*` **0 键**，且写的是 `rollup 4.63.3`，而磁盘 `node_modules/rollup` 是 **4.63.4**
—— **`node_modules` 已经不被锁文件描述**。而 `I39` 的成因（`todo.md:294`）正是"跑一次 `npm install` 就把
`@rollup/*`、`@esbuild/*` 剪掉，`npm run build` 直接失败"。

而 `W1-1`（`B3`）要装 `mathjs` —— **同一次 `npm install` 就会触发同一个坑**。

**处置**：
1. `W0-6` 不要"顺手单独做"：它与装 `mathjs` 是**同一次依赖操作**，应**合并成一件事**，一次承担风险、一次回归。
2. 顺序固定：**打包/录屏前不动依赖**；要动就一次动完 → 立刻 `npm run build` 验证 → 若平台包丢失，按
   `知识库.md` §13.3（`npm install --no-save` 装回）或 §13.4（离线 tgz + Python `tarfile`，脚本见 `.learnbuddy/tmp/fix_rollup.py`）恢复。
3. 锁文件重生成后，**必须**跑 `npm run verify:predeploy` **并**做一次容器构建（`Dockerfile:37` 去掉 `rm -f package-lock.json`）
   才能声称"根治"。只改锁文件不验证容器 = 又一次"看起来修好了"。

#### 订正 7 ｜ `W1-1` 的验收口径漏了一条硬约束：`mathjs` 是**同步计算**，"超时保护"按 `Promise.race` 写是**无效的**

`docs/tech/2026-09-17-符号验证引擎选型-纯TS.md:92-93` 写"仍设超时保护（包裹 `Promise.race` 或执行步数上限）"。
`Promise.race` **不能抢占同步计算**：`math.derivative` / `simplify` 一旦开始，事件循环被占住，
计时器回调根本轮不到执行 —— "超时"要等同步计算**结束之后**才可能生效，即它保护不了任何东西。

**处置**：实现时二选一，并**在文档里如实写明是哪一种**：
- ① **输入规模上限**（表达式长度 / 项数 / 取样点数的硬上限），超限即 `unverified` —— 成本低，**推荐**；
- ② 真超时只能用 `worker_threads` —— 成本高，不建议在 09-25 前做。

**不要保留"`Promise.race` 超时保护"这个说法** —— 它属于"看起来有、实际没有"的那一类。

#### 订正 8 ｜ 引用精度：`T-07` 被当成"`P-C14` 优先于一切拆分"的出处

`T-07` 的**本体**是"是否接受两条冻结线"（拆分计划书 §2.1、§18.8）。
"`P-C14` 仍优先于一切拆分"这句只出现在**§1.7 的 v1.1 修订表**里。父文档 §九 已自我要求
"引用决策时一律连内容一起写"，此处照办即可：写成「`T-07` 接受两条冻结线（§1.7 记：`P-C14` 仍优先于一切拆分）」。
这与 `I41`（`知识库.md` §14 的 `D1`/`D3` 各出现两次）是同一类引用陷阱。
