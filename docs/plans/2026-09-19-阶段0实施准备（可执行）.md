## 1. 阶段 0 九张实施卡

每张卡都是"照着做即可"。**顺序 = 卡号顺序**，卡内「依赖」为空即与其它卡并行安全。

### 卡 1 ｜ 安全响应头（C）

| 项 | 内容 |
|---|---|
| **落点** | 新增 `apps/server/src/http/security-headers.ts`，导出 `mountSecurityHeaders(app: Express): void`；在 `src/index.ts` 里**紧跟 logger 之后、所有路由之前**调用 |
| **为什么单独成模块** | 中间件必须对**所有响应**生效（含静态、`/api`、404、错误响应）。写在 `mountWebApp()` 里只覆盖页面 ✅ 会把 `/api` 与 404 漏掉；而 `mountWebApp()` 的文档明确要求"须在 `/api` 路由之后调用"，所以那里不是正确位置 |
| **头集合（阶段 0 版）** | `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'; object-src 'none'`<br/>`X-Content-Type-Options: nosniff`<br/>`X-Frame-Options: DENY`<br/>`Referrer-Policy: strict-origin-when-cross-origin`<br/>`Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`<br/>`Cross-Origin-Opener-Policy: same-origin`<br/>`Cross-Origin-Resource-Policy: same-origin` |
| **刻意不上** | ① `require-trusted-types-for 'script'` —— 计划书 §10.4.4 已判定"贸然开启会打挂页面"，留到阶段 8；② `Strict-Transport-Security` —— 平台中间页可能覆盖，**列为"尽力而为"**：只在 `req.secure === true` 时发送，并把线上实测结果记进当轮 review；③ `Cross-Origin-Embedder-Policy` —— 计划书结论是"评估后不加" |
| **头集合的实现形态** | 用**一个常量数组** `SECURITY_HEADERS: readonly [string, string][]` 定义 → 回滚＝注释掉一行挂载，不动其它逻辑（计划书 §14.1 回滚要求） |
| **配套断言** | `apps/server/scripts/verify-serve-web.mjs` 新增一节「安全响应头」，**10 条**：<br/>①–⑦ 六条头在 `/` 上存在且值精确匹配（CSP 逐指令比对，不做 includes）；<br/>⑧ 同一组头在 `/api/health` 上也存在（证明挂在全局而非仅静态路径）；<br/>⑨ 404 响应（`/nope.js`）上也存在；<br/>⑩ **不出现 `Access-Control-Allow-Origin`** 且**不出现 `Access-Control-Allow-Credentials`**（计划书 §10.4.3 v1.1 升级为两条）<br/>⇒ `serve-web` 28 → **38**，合计 403 → **413** |
| **验收命令** | 本地：起服务端后 `curl -sI http://127.0.0.1:3000/`、`curl -sI http://127.0.0.1:3000/api/health`、`curl -sI http://127.0.0.1:3000/nope.js`，三处都要有六个头；<br/>**人工**：浏览器打开页面 → 控制台**零 CSP 违规**（本机做不了浏览器验证 `I8`，这条必须由人工执行并留记录） |
| **风险与止损** | 🔴 CSP 是唯一"改错了会打挂页面"的一项。止损动作：先在本地起服务端、用真实产物打开页面确认无违规再提交；一旦浏览器出现违规，**回滚 = 注释一行**，不要在现场改 CSP 指令 |
| **依赖** | 无 |

### 卡 2 ｜ `ErrorBoundary`（A）

| 项 | 内容 |
|---|---|
| **落点** | 新增 `apps/web/src/app/providers/ErrorBoundary.tsx`（阶段 0 已建骨架目录，直接按终态放，不再"先放 components 再搬"）；`apps/web/src/main.tsx` 15 行处包裹 `<App />` |
| **行为要求** | 类组件（`getDerivedStateFromError` + `componentDidCatch`）；兜底 UI 必须**说清是哪个区域出错**并给"重新加载"按钮；**不得**吞掉错误而不显示（与 §9 真实性一致：出错了要让用户知道，不是静默画个空壳） |
| **粒度** | 阶段 0 先包**整页**一层；逐面板包裹属阶段 4（widget 改造时一起做），现在包细了反而要在阶段 4 重做两遍 |
| **配套断言（⚠️ 有坑，必须按这个写）** | `verify:render` 用 `react-dom/server`，而**SSR 下 ErrorBoundary 不生效**（`renderToStaticMarkup` 遇错直接抛，不会走 `getDerivedStateFromError`）。因此**不能**写"渲染一个会抛错的子组件、断言出现兜底文案"——那条断言要么报假失败、要么被人为绕过后恒真。**正确写法两条**：<br/>① 纯逻辑断言：直接调 `ErrorBoundary.getDerivedStateFromError(new Error('boom'))`，断言返回 `hasError: true`（不依赖渲染）；<br/>② 正常路径断言：无错时渲染子树，断言子内容出现**且**兜底文案不出现。<br/>⇒ `render` 98 → **100**，合计 → **415** |
| **验收** | **人工**（`I8`）：临时在 `TutorPanel` 顶部 `throw new Error('演示兜底')` → 只有该面板显示兜底 UI、页面其余部分正常；验完立即移除 |
| **回滚** | `main.tsx` 去掉包裹（一个文件一处改动） |
| **依赖** | 无。但**建议排在卡 6（骨架）之后**提交，避免"新建目录 + 新建文件"混在同一次提交里 |

### 卡 3 ｜ 请求超时与取消（A + 需 C 确认口径）

| 项 | 内容 |
|---|---|
| **落点** | `apps/web/src/api.ts`（计划书写 `shared/api/client.ts`，阶段 0 尚未拆，**就在原位置改**）；`useWorkbench.ts` 里 6 处调用点按需传 `signal` |
| **具体改动** | `request()` 增加：① 默认超时 `DEFAULT_TIMEOUT_MS`；② 可选 `signal` 参数（与内部超时用的 `AbortController` **组合**，任一触发即中止）；③ **区分两类中止**——超时 → 面向学生的可重试提示；用户主动取消 → **不报错、不提示**（取消不是失败） |

| **验收** | **人工**（`I8`）：浏览器 DevTools 把网络设为 Slow/offline → 到点出现超时提示、可重试、可取消（取消后按钮恢复、无报错弹条） |
| **回滚** | 取消"不改调用方即可"：只要默认超时值不变，行为等价；把 `DEFAULT_TIMEOUT_MS` 设为 0/不传即恢复原状 |
| **依赖** | 客户端超时口径需先定（本文件 §4 待拍板项 P-2） |

## 3. 每批的统一验收前置（照抄执行，别凭记忆）

```bash
# 前端改动
npm run typecheck && npm --cache D:/smallbox/Projects/LearnBuddy/.learnbuddy/cache-<唯一名> run verify:render -w @lc/web

# 服务端改动（必须先起 mock 服务端，且**先确认 3000 端口没有残留进程**）
netstat -ano | grep ":3000" | grep -c LISTENING     # 必须是 0
cd apps/server && MODEL_PROVIDER=mock PORT=3000 <repo>/node_modules/.bin/tsx src/index.ts &
npm --cache ... run verify:flow -w @lc/server
npm --cache ... run verify:predeploy                # build:clean → build → dist → serve-web → repo
```

> ⚠️ **本轮实测踩到的坑（务必写进流程）**：3000 端口若有**上一轮的旧服务端进程**残留，
> 新进程绑不上端口，探针会打到**旧代码**上，于是出现"断言失败但代码明明改了"的假失败。
> 本轮因此把已写的断言误判为失败一次，杀掉残留进程后复跑即全绿。
> **结论：跑 `verify:flow` 前先确认 `LISTENING` 计数为 0，再起服务端。**
