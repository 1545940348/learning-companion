# 赛题意图解码与产品设计审查

> 审查对象：`微积分学伴_项目说明书.md`（V1.1）
> 参照文件：`大湾区AI_Coding创新大赛_赛事手册.md`
> 审查角度：① 赛题真实意图　② 目标用户（学高数的大学生）视角　③ 说明书功能设计的不足与改进
> 日期：2026-09-16

---

## 一、赛题意图解码

### 1.1 表层意图（手册写明的）

- 用 LearnBuddy 做一个有"智能体"特质的 Web 应用；
- 方向一要求"为高校教与学场景构建智能提效工具，让 AI 成为师生教学**副驾驶**"。

### 1.2 深层意图（从评分与提交要求反推）

把四条提交硬性要求和评分权重放在一起看，主办方的真实诉求就非常清楚了：

| 证据 | 反推出的意图 |
|---|---|
| 必交「LearnBuddy 历史对话记录」 | 评委要看到**开发过程本身**，而不是只看成品 |
| 「AI 工具使用」独占 25% | LearnBuddy 的使用深度是被独立考核的一等指标，不是副产品 |
| 赛事名为 **AI Coding** 创新大赛，而非"AI 应用大赛" | 关键词是 **Coding 的过程** —— 用 AI 把想法变成代码的能力 |
| 优秀作品可入驻「高校联合 Skills 库，长期复用」 | 主办方想要**可沉淀的教学资产**，而不是一次性 Demo |
| 「禁止使用 AI 生成完整方案后直接提交（AI 是工具，不是替代者）」 | 需要**人的主导性证据** |

**结论：这场比赛的评分重心是"你如何用 AI 造出东西"，而不是"你造出了多复杂的系统"。**

这对微积分学伴有一个直接推论：说明书里那些**为了体现系统复杂度而设计的状态机、版本控制、三类来源校验**，对拿分的作用远小于"一条完整、可复现、有迭代痕迹的 AI Coding 过程记录"。说明书目前把 70% 的精力压在了"工程复杂度"上，而"AI 工具使用"这 25% 只是靠一句"每天保存真实 LearnBuddy 记录"来兜底，投入明显不足。

### 1.3 意图与选题的匹配度评估

方向一的关键词是"教学**管理**助手""师生教学副驾驶"。说明书对应的子项是"多模态教学智能体"（支持图文素材智能解析、知识点结构化抽取、交互式答疑辅导）——**匹配度良好**，三个能力点都在。

但要注意一个偏差：说明书写的是「**教学**管理助手」，实际交付的是「**学习**辅助工具」，全程只有学生视角，教师端明确不做（1.2 节"初赛不做"）。评审若较真"教学管理"四个字，可能追问"教师/教学管理的部分在哪里"。这是需要准备话术的点，不必改产品，但要在 PPT 里把"教学"解释为"教学过程（教与学）"。

## 二、用户视角：真实痛点是什么

> 用户画像：学习高等数学（一元微积分）的本科生，正在应付课堂、作业、期末考或考研。

按真实发生频率和情绪强度排序：

| 优先级 | 痛点 | 用户的原话大概是 |
|---|---|---|
| ① 最高 | **讲义/教材跳步**，公式突然出现，看不懂卡在哪 | "这一步是怎么来的？" |
| ② 最高 | **有题不会，问不到人**，搜题软件只给答案不给过程 | "答案是 2，可我要的是为什么是 2" |
| ③ 高 | **不知道自己哪里不会**，只知道"这章听不懂" | "我到底是导数没学会还是单调性没学会？" |
| ④ 高 | **答疑等待**远超注意力持续时间（老师 1:200，同学未必会，答疑要预约） | "我现在想搞明白，不想等明天" |
| ⑤ 中 | **符号/公式在通用聊天工具里显示混乱**，看不懂 | "这个 f'(x) 是啥符号？" |
| ⑥ 中 | **复习无重点**，不知道哪些是高频易错 | "这么多内容，先看哪个？" |

**注意 ① 和 ③ 的关系**：痛点 ③（不知道自己哪里不会）恰恰是说明书想解决的"前置知识缺口"，方向是对的。但说明书解决这个问题的方式，和用户期望的方式，差异很大——这是下文所有问题的根源。

## 三、用户真正想要的产品是什么样

用一句话概括用户期望：

> **一个永远不嫌你问得笨、打开就能用的私人数学家教。**
> 拍一张照片或粘贴一段文字 → 立刻得到"人话"解释 → 可以继续追问 → 顺手练两道 → 知道下一步看什么。

拆解为可交付的产品特征：

1. **零配置**：打开网页就能用，不需要注册、不需要上传"材料"、不需要理解任何概念。
2. **零门槛输入**：拍照、粘贴、手写都行，识别错了自动重试或直接问"是不是这个意思"，而不是要求用户校对。
3. **回答优先"解释跳跃的那一步"**：不是复述定义，而是补上老师默认你已掌握的那一步。
4. **可以无限追问**：像问人一样，"还是不懂""换个例子""为什么不能反过来"。
5. **主动诊断**：能告诉用户"你卡住是因为导数定义没掌握"，并且**立刻给出最小必要补充**，而不是让用户自己去找那份材料。
6. **即时的正反馈**：练完有反馈，能看到"我刚才不会，现在会了"。
7. **短**：一次回复三五百字能说清就别说一千字；用户在看手机。

## 四、用户希望省略的工作流（对照说明书逐条）

这张表是本次审查最核心的部分——**说明书里每一项"工程亮点"，在用户侧几乎都是一道额外的操作负担**：

| 用户根本不想要 | 说明书却要求用户做 | 摩擦等级 |
|---|---|---|
| 校对 OCR 结果 | 2.1 节：显示识别内容、标明模糊公式与待确认项，**学生确认后才更新材料** | 🔴 极高 |
| 管理学习资料 | 2.1 节：每会话最多 3 份材料、合计 9000 字、超限需"缩短或开始新学习" | 🔴 极高 |
| 选择"补充材料"还是"新学习" | 2.3 节：两种上传动作，且"开始新学习"会**清空全部状态** | 🔴 极高 |
| 理解知识库状态概念 | 3.1 节：LOCAL / MISSING / 待确认 三态 | 🟡 高 |
| 理解权限开关 | 4.2 节：外部参考开关，**默认关闭** | 🔴 极高 |
| 自己去补前置知识 | 2.2 节提示："也可以补充讲义，或开启 AI 外部参考" | 🔴 极高 |
| 读知识点卡片 | 2.2 节：每会话展示 3–6 张卡片（名称/解释/公式/条件/来源/误区） | 🟡 中 |
| 做固定的单选题 | 2.4 节：每主题 3 道自编单选题 | 🟡 中 |
| 区分三类来源 | 4.3 节：讲义原文 / 基于材料的推导 / AI 外部参考 | 🟡 中（用户其实无感） |

### 4.1 最致命的一条：缺口提示在用户视角下是"推诿"

说明书的招牌功能是：

> "这部分需要导数知识，当前材料没有解释。你已掌握可以继续；也可以补充讲义，或开启 AI 外部参考。"

请代入学生视角读一遍这句话。学生的真实反应是：

> **"我不是上传了讲义才来问你的吗？你又让我去找一份导数笔记？我要是知道导数在哪，我还用得着问你吗？"**

这就是本项目最大的**产品认知错位**：
- 在**技术评审**视角，这是"诚实、有据、不幻觉"的加分设计；
- 在**用户**视角，这是"系统承认自己不会，并把补齐材料的责任推回给用户"。

更严重的是**默认状态死锁**：外部参考**默认关闭**，意味着在默认设置下，系统发现缺口后**不提供任何解法**——只能要求学生自己去找到一份"导数定义讲义"。而现实中学生的讲义就是同一份跳步的讲义，他找不到额外材料。**产品在默认配置下走不出缺口。**

### 4.2 第二个问题：把"材料治理"的成本转嫁给了学生

说明书花了大量篇幅定义材料的版本、上限、补充规则、会话隔离、状态失效（5.3 节）。这些是**知识库管理员**的工作，不是**学生**的工作。学生的心智模型里根本没有"会话/材料版本/授权许可"这些对象，他只有"我的一道题"和"我的一个问题"。

**一个学生打开网页只想问一道题，说明书却要求他先建立一个"学习会话"，上传并确认材料，等待系统抽取知识点、检查依赖——两步之后才允许提问。**

## 五、说明书功能设计的具体不足

以下按严重程度分级。🔴 = 影响产品成立；🟡 = 影响体验或投入产出；⚪ = 表述/一致性问题。

### 🔴 5.1 缺少"直接提问"的轻路径

全流程强绑定"上传 → 确认 → 抽卡片 → 查依赖 → 答疑"，没有"我就想问一道题"的入口。而**裸提问是学生 90% 的真实场景**。建议：允许在零材料状态下直接提问，系统用通用知识回答但标注"未基于你的材料"，材料只是可选增强。

### 🔴 5.2 外部参考开关默认关闭 = 默认不可用

见 4.1。至少应改为：**缺口出现时，在提示里提供"一键用标准教材知识补充并标注"的按钮**，把开关从"全局权限"降级为"单次操作的选项"。标签和溯源都保留，但不要让学生来决定系统的能力边界。

### 🔴 5.3 "确认识别结果"是反用户设计，数学场景尤甚

用户上传图片的目的就是**不想打字**。而要求学生核对数学公式的 OCR 结果，等于要求一个"本来就不会这部分内容"的人去做他做不到的校对。建议：**默认信任识别结果直接进入回答**，把识别文本以可编辑形式展示在旁边，用户发现问题再改。从"确认后使用"改为"使用中可纠正"。

### 🔴 5.4 材料上限与"新建清空"造成高频数据丢失

3 份 / 9000 字上限，而一份讲义照片往往就接近上限；"开始新学习"清空一切且不可恢复；"不承诺关闭会话后恢复"。学生会反复丢失上下文。建议：提高到 10 份 / 30000 字；把"新学习"从"清空"改为"新建标签并存"，旧会话可回看。

### 🔴 5.5 砍掉 AI 追加练习，砍错了地方

1.2 节把"AI 追加练习"移出初赛。但从用户视角看，**"按我上传的这份讲义给我出两道题"是仅次于"听懂"的第二大诉求**，也是最有产品感的瞬间。相反，被保留的是"每主题 3 道项目自编单选题"——固定、可背、与用户上传的讲义无关。

> 这是个方向性取舍失误：**保留了一个静态题库，砍掉了一个动态能力。**

建议：固定题作为兜底保留 3–6 道以保证演示可控；**把 AI 出题做成最小版**（基于当前已确认材料生成 1–2 道，附解答与依据标注），这同时还能增值"技术创新"分。

### 🟡 5.6 三类来源 + 引用校验：投入产出严重错配

4.3 节要求每个回答块返回来源类型和引用，B 校验结构/编号/摘录匹配，E7 要求"假引用不能作为正常答案展示"。这块工程量很大（提示词约束 + 结构化输出 + 校验器 + 失败重试），但**用户对"这是讲义原文还是推导"几乎没有感知**——他只关心对不对、懂不懂。

建议：保留能力，**降低用户界面权重**——默认给简洁答案 + 引用角标（可展开溯源），把三标签藏进"依据详情"。省下的工时投给 5.5 的 AI 出题和 5.1 的轻路径。

### 🟡 5.7 状态机复杂度超出 10 天 3 人×2 小时的预算

说明书自定的约束是 **3 人 × 每天 2 小时 × 10 天 ≈ 60 人时**。而 P0 清单包含：4 个接口、三层架构、依赖三态机、材料版本递增、旧响应失效、授权变更丢弃、4 个测试素材主题共 6 份、12 个答疑问题、9 道题、E1–E10 边界测试、3 分钟视频、8 页 PPT、部署与提交。

粗估工作量：

| 模块 | 估时 |
|---|---|
| 前端交互（输入/卡片/答疑/练习/异常态/窄屏） | ~20 h |
| 后端服务与 4 个接口、会话版本控制 | ~15 h |
| 教学模块（提示词、依赖分析、来源校验） | ~15 h |
| 素材、9 道题、数学核对 | ~10 h |
| E1–E10 边界测试与修复 | ~8 h |
| 视频、PPT、记录整理、提交 | ~10 h |
| **合计** | **~78 h** |

**即存在约 30% 的工时赤字。** 说明书里"22 日阻断清零 / 23 日冻结功能"的排期过于乐观，实际会在 21 日左右被迫临时砍功能——而临时砍功能往往砍在用户最在意的地方。

建议：**现在就主动砍**，而不是等 21 日被迫砍。优先砍 5.6 的用户界面权重和 5.7 中的部分状态管理规则（例如简化材料版本失效策略，只要保证"换会话不串扰"这一条）。

### 🟡 5.8 核心亮点"缺口检测"的可验证性偏弱

依赖判断由模型生成，判定标准是"足以支持当前学习目的"——这句话可操作化程度低。E1/E2/E3 靠人工核验，评审拿到作品后难以复现，且模型输出不稳定。演示成功 ≠ 真实可用。

建议：为"缺口检测"准备一个**极小但极稳的判定规则表**（3 个主题 × 各 2–3 条前置关系，固定的关键词/结构标准），把模型的自由度限制在可控范围内。

### 🟡 5.9 没有留存感：用完即走，看不到积累

明确不做长期画像、没有错题本、没有进度。演示够用，但产品不成立：用户第三次打开时，一切从零开始。

建议：用 `localStorage` 做一个最小"学习记录"（问过的问题、做错的题、已补齐的缺口），成本极低，但能让用户感到"我在积累"。

### ⚪ 5.10 演示主线选择的偏差

视频脚本 1:20 的重心放在"补充后依赖更新"——这是**第二顺位**的用户场景，且需要用户主动做两次上传。而用户最高频的场景（拍照问一道题 → 听懂）没有在视频主线里。

建议：**双主线**。前 60 秒走"30 秒听懂一道题"的高频爽点，中段 60 秒展示"缺口发现与补齐"作为技术亮点，后段展示来源与边界。这样既让评委共情用户，又拿到技术创新分。

### ⚪ 5.11 几处文档表述问题

- 1.2 节"P0 必须完成"清单包含 11 项，与 60 人时预算不匹配（见 5.7）。
- 3.1 节"待确认"状态与 3.2 节更新规则未说明"待确认"最终如何收敛。
- 5.3 节"不承诺跨设备与关闭会话后恢复"——学生手机拍照、电脑看题是真实场景，建议至少支持导出/复制会话。
- 6.2 节 A"不修改模型提示词或保管 API 密钥"合理，但 A 作为唯一做界面的人，若不能看到真实模型输出，界面容错设计会脱离实际，建议给 A 一个只读的真实接口调试通道。

## 六、改进建议（按优先级与性价比排序）

| 优先级 | 动作 | 成本 | 收益 |
|---|---|---|---|
| **P0** | 把外部参考开关默认改为开启，或在缺口提示中加"一键补充标准知识" | 极低 | 解除默认死锁，直接提升用户体验分 |
| **P0** | "确认识别结果"改为"默认信任 + 可编辑纠正" | 低 | 砍掉最大的一道输入摩擦 |
| **P0** | 增加零材料的"直接提问"入口 | 低 | 覆盖 90% 真实场景 |
| **P1** | AI 出题恢复为最小版（基于材料生成 1–2 题） | 中 | 补上用户第二大诉求，且增值技术创新分 |
| **P1** | 三类来源从"用户可见标签"降级为"可展开溯源" | 中（净省时） | 省工时 + 界面更干净 |
| **P1** | 放宽材料上限至 10 份 / 30000 字；新学习改为并存而非清空 | 低 | 消除高频数据丢失 |
| **P2** | 加最小错题本 / 学习记录（localStorage） | 低 | 建立留存与"进步感" |
| **P2** | 缺口判定改为固定规则表 + 受控模型自由度 | 中 | 提高可复现性与演示稳定性 |
| **P2** | 把 "LearnBuddy 使用记录" 升级为每日结构化日志 | 低 | 直接服务 25% 的 AI 工具使用得分 |
| **P3** | 视频改为双主线（高频场景 + 技术亮点） | 低 | 用户体验分 + 评委共情 |

### 6.1 关于 25% 的「AI 工具使用」——目前投入最不足的一项

说明书对这块只有一句话："每天各保存真实 LearnBuddy 记录"。

25% 的分值不该只靠"保存记录"来兜底。建议做成**可提交的资产**：
- 每天一条结构化记录：**目标 → 向 LearnBuddy 提了什么 → 得到什么 → 人工如何验证/否决 → 修正后结果**；
- 保留"AI 说错了，我发现并纠正"的案例——这恰恰是手册 8.3 节"AI 是工具不是替代者"最有力的合规证据；
- 做成时间线文档（含截图），而不是散落的对话截图。

**这一项的单位投入产出比高于说明书里任何一项后端状态管理。**

### 6.2 两条容易拿的加分项

- **跨专业组队 +2 分**：手册明确"2 个及以上不同专业/院系"，建议核实现有 3 人是否已满足，若满足务必在报名信息与 PPT 中明确标注。
- **社交媒体传播 +1 分**：要求"过程设计完整，不能是简单的几句话 + 2–3 张配图"。可用"10 天 AI Coding 造一个数学家教"的连载形式（Day1…Day10），成本低且与开发记录复用。

### 6.3 合规风险提示

手册 8.3 节明令禁止"使用 AI 生成完整方案后直接提交"，而说明书 1.4/8.2 节自述"使用 Agent 辅助开发"。**这两者的边界只能靠人工留痕来证明。** 建议三人各自的记录中，必须体现：
1. 人提出目标与约束；
2. 人验收 AI 输出并挑出问题；
3. 人做出取舍决策（例如"为什么砍掉 AI 追加练习"）。

---

## 七、必须守住的亮点（不要为了改而改）

改动的目的是去掉用户摩擦，**不是削弱技术叙事**。以下设计建议原样保留：

1. **前置知识依赖建模 + LOCAL/MISSING 三态** —— 这是本项目最有辨识度的技术创新点，只是要把"责任在用户"改为"责任在系统"。
2. **三类来源与引用校验** —— 保留能力与标签，只降低界面权重。
3. **回答边界与"条件不足"的处理**（4.1 节）—— 这是 AI 教学工具最容易被评审认可的专业性体现。
4. **会话隔离与旧响应失效**（E8/E10）—— 保留最小必要部分，证明工程严谨。
5. **"不伪装成上传讲义原题""不以模拟行为冒充真实能力"** —— 这种诚实性在评审中是加分项，也契合规要求。

---

## 八、一句话结论

> **方向是对的，机制是硬的，但产品把"知识库治理的责任"放在了用户肩上。**
>
> 微积分学伴的技术叙事（前置缺口识别 + 来源可溯）在评审桌上是亮点；但它要求用户在提问前先成为自己资料的图书管理员——上传、校对、控量、补料、理解状态与权限。学生要的只是一个答案和一个解释。
>
> 核心动作就三件：**把默认打开（外部参考）、把确认变可选（识别纠正）、把答疑变轻（直接提问）**。
> 加上一件战略动作：**把 25% 的 AI 使用分从"保存记录"升级为"结构化过程资产"**。
> 这四件事的投入，低于说明书里任何一个后端状态管理模块，但对最终得分的影响更大。
