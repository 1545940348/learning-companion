## 二、缺陷与根因

### 缺陷 1：模型故障一律变成 500

`errorHandler` 只识别 `ApiError`、`SessionNotFoundError` 与本项目上一轮新增的
`SessionVersionConflictError`。**`ModelError` 完全没被识别**，于是落到最后的兜底分支：

```ts
const isTimeout = error instanceof Error && error.name === 'AbortError';
// ModelError 的 name 是 'ModelError'，所以这里为 false
code: isTimeout ? 'MODEL_TIMEOUT' : 'INTERNAL',   // → 一律 INTERNAL
```

后果：**认证失败、额度用尽、上游故障、超时，前端全都只看到 500 INTERNAL**，
无法据错误类型给出不同的下一步 —— 而 `packages/contracts` 里
`ModelErrorCode` 的注释写得很清楚：「前端与教学模块需要据此给出不同的下一步（重试 / 报错 / 引导），**而不是一律 500**」。

**这是上一轮自测时顺带发现的**（用 `MODEL_TIMEOUT_MS=1` 注入超时，结果返回 500）。

### 缺陷 2：60 秒是"每次调用的超时"，不是"每次请求的预算"

`MODEL_TIMEOUT_MS` 目前只在单次模型调用上生效。经查，**每个接口目前恰好只调用模型 1 次**，
所以 60 秒"碰巧成立"。但：

- 只要加重试（一次请求两次调用），总耗时就可能变成 120 秒；
- 将来任何接口需要两步模型调用（如"先解析再讲解"），同样会破。

**即预算不是被"实现"了，而是被"绕过"了。**

## 四、错误映射表

| 模型错误 | HTTP | `error.code` | `retryable` | 前端该做什么 |
|---|---|---|---|---|
| `AUTH` 认证失败 | **401** | `MODEL_ERROR` | false | 提示服务端凭证异常；重试无用 |
| `QUOTA` 额度不足 | **429** | `MODEL_ERROR` | false | 提示额度不足 |
| `TIMEOUT` 超时 | **504** | `MODEL_TIMEOUT` | **true** | 一键重试（输入已保留） |
| `UPSTREAM` 上游故障 | 502 | `MODEL_ERROR` | **true** | 可重试 |
| `INVALID_REQUEST` 请求不合法 | 400 | `MODEL_ERROR` | false | 属我方缺陷，需修代码 |

### 为什么没有新增错误码（经负责人确认）

`ApiErrorCode` 是 `packages/contracts` 的**契约类型**，增加取值需要 A、B 同步修改，
而 V1.4 明确要求「避免文档、前端和服务端分叉」。

因此：**契约层只区分 `MODEL_TIMEOUT`（超时）与 `MODEL_ERROR`（其他模型故障），
细分类别由 HTTP 状态码承载。**

**取舍的代价（如实记录）**：前端无法只凭 `error.code` 区分"认证失败"与"额度不足"，
必须看状态码。若将来需要更细的 `code`，那是一次独立的契约变更，需 A 配合。

## 五、60 秒预算的设计

```
请求进入
  → createBudget(env.modelTimeoutMs)        开预算
  → withBudget(adapter.call, budget)        包装 ModelCaller
  → 教学模块调用模型时，拿到的 timeoutMs = min(调用方指定值, 剩余时间)
```

**三个要点：**

1. **每次调用拿剩余时间，不是各自重新计 60 秒。** 实测日志可见 `timeoutMs: 799`
   而配置是 800 —— 差的那 1 毫秒就是已经流逝的预算。
2. **预算耗尽时直接抛 `TIMEOUT`，不发起调用**（避免明知超时还去打一次上游）。
3. **调用方显式传的 `timeoutMs` 也受总预算截断**（取两者较小值），
   否则单次调用可以突破总预算。

## 六、重试策略

| 错误类型 | 重试吗 | 理由 |
|---|---|---|
| `UPSTREAM` | ✅ **最多 1 次**，且剩余 ≥ 5000 ms 才动手 | 5xx / 网络抖动是唯一"再试一次可能成功"的情形 |
| `TIMEOUT` | ❌ | 预算通常已耗尽，没有余量 |
| `AUTH` | ❌ | 凭证错，重试一百次结果一样 |
| `QUOTA` | ❌ | 额度空，重试只会再失败一次 |
| `INVALID_REQUEST` | ❌ | 我方请求有问题，重试等于把同一个错发两遍 |

**三个条件同时满足才重试**：错误类型可重试、重试次数未用尽、剩余预算够再跑一次。

## 八、过程中的一次测法修正（如实记录）

第一次验证超时映射时用了 `MODEL_TIMEOUT_MS=1`。结果确实返回了 504，
但**它走的是"预算在调用前就耗尽"的路径，模型调用根本没被发起**（日志为空即是证据）。

**因此这条测试没有覆盖"适配层真的超时"的情形。** 改为 `MODEL_TIMEOUT_MS=800` 重测，
才真正走到适配层并打出 `model.call.start` / `model.call.fail`。

**教训**：注入式测试要确认**注入点落在你想验证的那条分支上**，
否则会拿到"结论正确但路径不对"的虚假通过。
