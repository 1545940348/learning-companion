## 1 问题

**`npm run build` 成功，但 `node dist/index.js` 启动即崩：**

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module
  'D:\...\packages\contracts\src\session.js'
  imported from 'D:\...\packages\contracts\src\index.ts'
```

影响：**四件套第一件「在线链接」无法交付** —— 部署形态根本起不来。
这不是"稳定性不足"，是**不可运行**。

---

## 2 根因

三件事叠加：

1. `packages/contracts` 与 `packages/teaching` 的 `package.json` 把
   `main` / `types` / `exports` **全部指向 TypeScript 源码** `./src/index.ts`
   —— 这是为了让 `tsx` 与 Vite 直接消费源码，开发期很舒服。
2. 两个包的**源码内部用 ESM 后缀互相引用**（`import './session.js'`，而实际文件是 `session.ts`）。
3. `tsup` 默认把 `package.json` 的 `dependencies` 当作 external，
   于是产物里**保留了对这两个包的导入**。

结果：开发期的 `tsx` 能做 `.js → .ts` 的映射，**原生 node 不能**。
node 加载了 `index.ts`（Node 的类型擦除），却解析不到 `./session.js`，进程启动即退出。

**最危险的地方在于：构建输出里毫无迹象。** `npm run build` 打印 "Build success"，
问题只在**真正把产物拉起来**时才暴露。

---

## 3 试过的方案（含被否决的）

| # | 方案 | 结果 |
|---|---|---|
| 1 | `tsup --no-external @lc/contracts --no-external @lc/teaching` | ❌ **tsup CLI 不支持 `--no-external`**，cac 报 ``option --external <name> value is missing`` |
| 2 | `tsup.config.ts` 里写 `noExternal: [/^@lc\//]` | ❌ 构建时被 safe-delete 拦：tsup 经 `bundle-require` 会生成并删除临时配置文件 `tsup.config.bundled_*.mjs`，本环境删除被阻 |
| 3 | 换成 `tsup.config.mjs`（无 import 的纯对象） | ❌ 同样被拦 —— **说明本环境任何 tsup 配置文件都不可用**，与配置内容无关 |
| 4 | **把 `@lc/contracts`、`@lc/teaching` 从 `dependencies` 移到 `devDependencies`** | ✅ **采用**。tsup 不再把它们当 external，esbuild 直接内联 |

## 4 最终方案

### 4.1 改动

`apps/server/package.json`：
- `dependencies` 只留真正的第三方运行时依赖：`@tencent-ai/agent-sdk`、`dotenv`、`express`
- `devDependencies` 增加 `@lc/contracts`、`@lc/teaching`
- `build` 脚本保持 CLI 形式不变（`tsup src/index.ts --format esm --out-dir dist --sourcemap --clean`）

### 4.2 为什么是内联

`@lc/*` 是**不对外发布的私有包**，本项目又是**单 Web 服务**。内联不产生复用损失，而且：

1. 不需要给两个包补构建步骤 —— 否则会引入新的状态漂移
   （`tsx` 开发期到底读 `src` 还是 `dist`？多一个"产物是否最新"的坑）；
2. 产物不依赖 `node_modules` 里的 workspace 软链，部署更省事。

**代价（如实记录）**：产物由 56.5 KB 增至 **78.2 KB**；改动两个包后必须重新构建才生效。
对单服务部署可接受。

### 4.3 为什么放 `devDependencies` 在语义上也说得通

内联之后，这两个包**在运行时确实不再被需要** —— 它们只是构建期输入。
`dependencies` 表达的是"运行时需要解析的依赖"，把它们留在那里反而与事实不符。

⚠️ 副作用：若生产环境用 `npm ci --omit=dev` 安装后再构建，会因缺少这两个包而失败。
**正确顺序是"装全量依赖 → 构建 → 再用产物运行"**（部署流程已按此写明）。

### 4.4 新增回归保护

单靠"构建成功"发现不了这类问题，因此新增 `apps/server/scripts/verify-dist.mjs`：

```
npm run build -w @lc/server
npm run verify:dist -w @lc/server      # 构建 → 真实启动产物 → 打接口 → 关闭
```

覆盖 8 项：产物存在 / **以原生 node 启动成功** / health 200 / health 如实报 mock /
health 含验证引擎状态 / session 201 含空图谱 / quiz 返回固定题 / graph 可读。

**与其它脚本的分工**：
`verify:all`（离线纯函数）→ `verify:flow`（真实 HTTP，开发期运行器）→
**`verify:dist`（真实 HTTP，构建产物）** —— 只有最后一个覆盖"部署形态"。

## 6 已知限制与后续

1. **本环境无法使用 tsup 配置文件**（safe-delete 拦截 `bundle-require` 的临时文件）。
   因此本方案依赖"tsup 默认不为 devDependencies 里的包生成 external"这一行为。
   若将来必须写 `tsup.config.*`（例如需要多入口），**在能正常删除临时文件的环境中开发即可**，
   本方案不构成长期阻碍。
2. **产物变大约 38%**。若将来关注启动内存或冷启动，可改为给两个包补构建步骤。
3. **`verify:dist` 未并入 `verify:all`**：它需要先构建、且会占用端口，不适合放进离线套件。
   建议在部署流程中固定执行。
4. `verify:flow`（30 项）当前位于 `feat/a-material-path` 分支的提交中，
   本次验证是临时从该分支取出脚本执行的。**合并后应把它与本脚本一并列入部署前检查清单。**
