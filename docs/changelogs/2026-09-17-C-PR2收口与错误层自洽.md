## 二、为什么这么改（逐条对应评审发现）

### P1-1 + P1-2：错误层不再"一处一个答案"

**问题**：`errorHandler` 的 `ApiError` 分支把 `retryable` 硬编码为 `false`，
而提交复核分支返回 `true`。同一个 `SESSION_STALE` 因此有两副面孔；
前端 `apps/web/src/api.ts` 只读 `retryable`，入口路径的学生拿不到"一键重试"。
同一函数的兜底分支还把 `INTERNAL` 标成可重试，并把内部报错原文回给客户端。

**改法**：`retryable` 一律由错误码查表推导，`ApiError.status` 也由错误码推导。
`SESSION_STALE` 的两条路径都走 `defaultStatusForApiCode('SESSION_STALE')`，
**结果必然相同**（409 / retryable:true）。

**唯一保留的例外**（代码注释里写明理由）：`ModelError` 的 5 分类比 `ApiErrorCode`
的 `MODEL_ERROR` 更细 —— `UPSTREAM` 可重试、认证失败不可重试，两者都映射到
`MODEL_ERROR`。此时以**更细的码**为准，由 `model-error-map.ts` 提供。

### P1-2：请求体解析失败归 400

畸形 JSON 原会落到兜底 → **500 `INTERNAL`** + 解析器原文。现由 `classifyBodyError()`
识别 `entity.parse.failed` / `entity.too.large`，分别返回 **400** / **413**，不回显解析器 message。

### P1-3：轻路径省略 `sessionId` 不再被当成越权

原 `requireAuthorization: body.sessionId !== null`：字段省略时 `undefined !== null` 为真
→ 零材料提问被判「AI 补充内容未经学生授权」（实测 400 `UNAUTHORIZED_CONTENT`）。

**实际改法与计划不同**：计划写的是改成 `Boolean(body.sessionId)`，实现改为**先校验**
`sessionId` 必须是 `string | null`（契约里它是必填字段），省略或类型不对就明确报 400
并提示"轻路径请显式传 null"。理由：`Boolean()` 会把调用方写错当成合法轻路径静默放过，
而契约已把它定义为必填 —— **报错文案必须与真实原因对得上**。
A 的 `App.tsx:35` 本来就传 `sessionId: null`，因此无回归。

### P2-1：入参形状校验

`materials` 传字符串或缺 `text` 的元素，原会在 `checkMaterialQuota` 抛 `TypeError`
→ 500 且回显 `Cannot read properties of undefined (reading 'length')`。
现由守卫拦在入口：`materials` 必须是数组、元素必须有非空字符串 `id` 与字符串 `text`、
`kind` 限 `upload | ai-supplement`；`createdAt` 由服务端兜底、`kind` 缺省为 `upload`
—— **能合理兜底的字段不收紧**，避免为了严格而拦住 A 的正常调用。

### P2-2：`error.cause` 不再被丢弃

Node 的 `fetch` 只抛 `TypeError: fetch failed`，DNS／证书／连接被拒都在 `cause` 上。
V1.4 把"云端独立验证"列为唯一挡住交付的事项，而云端最常见的失败正是这一类。
`describeError()` 展平最多 4 层错误链后再脱敏。实测：

```
改前： "detail": "TypeError: fetch failed"
改后： "detail": "TypeError: fetch failed ← Error: bad port"
```

### P2-3：记录实际型号与用量

说明书 V1.4 §5.2 要求「返回值可用时记录实际型号」。现把响应回显的 `model`/`usage`
记入 `model.call.meta`：

```
INFO model.call.meta {"requestedModel":"probe-model","actualModel":"probe-echo-model",
                      "usage":{"prompt_tokens":10,"completion_tokens":20}}
```

配置的 `DEEPSEEK_MODEL` 是**请求**型号，与实际服务型号未必相同；若上游是网关、
对型号名照收不误，这行日志是唯一能发现的地方。

### P3：细节

- 预算文案秒数跟随 `MODEL_TIMEOUT_MS`（实测 `MODEL_TIMEOUT_MS=1` 时提示"1 秒"）。
- `/api/*` 未匹配路径返回统一 JSON 404，不再是 Express 默认 HTML 页。
- `/quiz` 校验 `topic`/`source`：非法 topic 由"200 + 空数组"改为 400。
- 配额提示含本次份数：实测一次提交 4 份时提示"当前已有 0 份，本次提交 4 份，合计 4 份"。
- `model/index.ts` 目录注释与事实对齐。

## 三、状态码的两处**有意变更**（请 A 知悉）

| 契约错误码 | 改前 | 改后 | 理由 |
|---|---|---|---|
| `SESSION_STALE` | 入口 400 / 提交复核 409 | **统一 409** | 同一件事必须同一答案；409 语义更准确 |
| `UNAUTHORIZED_CONTENT` | 400 | **403** | 是"内容不允许展示"，不是"请求格式不对" |

**契约未改动**：`ApiErrorBody` 只声明 `{ code, message, retryable }`，不含状态码，
因此这两处不构成契约变更，A、B 无需改类型。A 的 `api.ts` 只读 `retryable`，对它透明。

## 五、实现过程中被自己推翻的三处（如实留痕）

1. **`respond()` 第一版让 `ModelError` 也按 `ApiErrorCode` 推导 `retryable`**，
   导致 `UPSTREAM` 从"可重试"退化为"不可重试"。被本轮新增的回归脚本当场抓出
   （3 项失败），随即改为"更细的码说了算"，并补了 5 分类断言。
   —— 这正是本次修复的主要风险点，靠测试而非目测挡住。
2. `request-guards.ts` 编辑中误留一个无意义占位函数 `guardOptionalText_placeholder`，已删除。
3. 自建探针第一版在 `r.json()` 之后又调 `r.text()`，报 `Body is unusable` 而整体中断，
   改为先取文本再解析。属测试代码自身缺陷，不影响被测服务。
