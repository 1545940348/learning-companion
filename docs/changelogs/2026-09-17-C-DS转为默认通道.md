## 一、为什么改

说明书 V1.4 把默认推理通道从 CodeBuddy Agent SDK 改为 **DeepSeek API**，依据是负责人反馈的
**平台调用超时问题**（SDK 通道实测文字 12–21 秒、图片 17.7 秒，撑不住"30 秒得到解释"的口径）。

V1.4 同时点名了本次要处理的缺口：

> 「当前代码仍将DS作为显式备选，`auto`仍偏向SDK；**C下一轮需同步默认配置、说明及诊断文案。**」

## 三、三条关键设计决定

### 1. 取消 `auto` 档，而不是"让 auto 偏向 DS"

V1.4 的要求是"**默认配置为 `MODEL_PROVIDER=deepseek`**"。若保留 `auto` 并让它偏向 DS，
它就仍会因有无 SDK 密钥而在两条通道间摇摆 —— 那正是 V1.4 要消除的不确定行为。
**因此直接取消 `auto`**：不确定的档位不存在，就没有"隐性切换"的空间。

### 2. 配置不完整 → 明确报错并**拒绝启动**，不是"警告后继续"

V1.4 要求"缺少DS密钥或模型失败时明确报错，不静默切SDK或mock"。
若只警告后继续，服务会正常启动、然后在学生第一次提问时才暴露 —— 那对演示是最坏的时机。

**注意区分两类失败**（这也是"不崩主进程"的落实方式）：

| 类型 | 处理 | 是否退出 |
|---|---|---|
| **配置问题**（取值非法、缺密钥、缺型号） | 启动时汇总打印 | **是，主动 `exit(1)`** |
| **运行时失败**（网络、超时、401、额度） | 适配层捕获为 `ModelError`，经 `errorHandler` 映射为可重试错误 | **否**，进程不受影响 |

### 3. 移除 `DEEPSEEK_MODEL` 的代码默认值

V1.4：「已有代码中的默认型号**不是验证依据**；`DEEPSEEK_MODEL`须填写真实可用型号」。
因此改为必须显式配置，`.env.example` 中给出已验证的值供复制。

## 五、一个重要发现：DS 的 JSON 能力明显强于 SDK

| | JSON／结构化输出 |
|---|---|
| CodeBuddy Agent SDK | **两次实测均不生效**（`outputFormat` 被忽略，模型输出 markdown，enum 不受约束） |
| DeepSeek API | **生效** —— 提示词方式即返回干净可解析的 JSON，字段完整 |

这印证了 V1.4 那句「**SDK 曾未兑现强制 schema，此结论不能直接套用 DS**」。

**本次仍未启用 DS 原生的 `response_format: json_object`** —— 提示词方式已足够，
在未单独验证该字段前不引入额外变量。**无论走哪条路，B 仍需做运行时字段与来源校验。**
