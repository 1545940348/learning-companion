## 2 为什么这么做（关键取舍）

1. **历史扫描不用 `git grep`**：`git grep -E` 走 POSIX ERE，不支持 `(?:…)`；
   若用它，历史与工作区**必须写两套正则** —— 两套必然漂移，而**"历史扫描悄悄失效"最危险**
   （它给的是虚假的安全感）。改用 `git cat-file --batch` 把 blob 取到 JS 里扫，**只有一套规则**。
2. **不手改 `package-lock.json`**（见 §3 事故）：手改需要完整传递依赖树与 integrity 哈希，
   改一半会产出比"不同步"更糟的状态。改为把"跑一次 `npm install` 收尾"作为**登记在案的待办**。
3. **不用自研 dev 启动器替掉 `concurrently`**：考虑过（这样能绕开锁文件问题），
   但自研进程管理器要处理 Windows 信号与子进程回收，**用一个新问题换一个旧问题**，否决。
4. **不越界实现 B 侧**：见 §4。

## 5 一处必须如实记录的事故（我自己造成的）

### 5.1 事件

在执行 `npm install --save-dev concurrently` 时，npm 在收尾阶段被系统拒绝（先 `EPERM` 于
`package-lock.json`，后 safe-delete 钩子 `ETIMEDOUT`），**而它已经删掉了
`@rollup/rollup-win32-x64-msvc` 却没装上新的** → `npm run build` 直接挂
（`Cannot find module @rollup/rollup-win32-x64-msvc`）。

- **根因**：锁文件里**没有** rollup 的平台包条目，npm 把已装的平台包当 extraneous 删除；
  随后自己失败，回不去。
- **恢复**：绕开 npm，按 `node_modules/rollup/package.json` 的版本号从 registry 下载 tgz，
  用 Python `tarfile` 解压到 `node_modules/@rollup/rollup-win32-x64-msvc/`
  （**全程无删除操作**）。已恢复并重新构建通过。
- **处置**：事故、根因与恢复手段写进 `docs/知识库.md` **§13.4**，脚本留在
  `.learnbuddy/tmp/fix_rollup.py` 备查。

### 5.2 同一根因引出的一步改进

`verify:predeploy` 第一次运行时不是被上面的问题卡住，而是被**同一类**问题卡住：
`build` 里的 `tsup --clean` 需要删除旧 `dist/`，safe-delete 拦下 → build 失败 → 整条命令失败。

**一个"部署前必跑"的命令在某台机器上跑不起来，就等于又回到"靠人记得"** —— 这正是它要消除的东西。
处置：新增 `npm run build:clean`，把旧 `dist/` **改名挪进 `.learnbuddy/trash/`**（改名不是删除，
不会被拦；该目录已 gitignore）。对构建而言与 `--clean` 等价。
移动失败时**只警告不阻断** —— 不要把"清理没做成"伪装成"构建失败"。
现在 `npm run verify:predeploy` 端到端 exit 0。
