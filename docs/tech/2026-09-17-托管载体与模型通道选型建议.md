## 1 D4：在线链接的托管载体

### 1.1 先把约束钉死（这些不是偏好，是硬条件）

| # | 约束 | 来源 | 后果 |
|---|---|---|---|
| C1 | **必须有一个活着的前端 + 后端** | 前端所有功能都走 `/api`，没有后端就是死页面 | §8.1 判定「只有静态页」= **不合格**，所以"传个静态站上去"这条路直接排除 |
| C2 | **评委无需配置任何密钥** | 四件套第 1 条、§4.3 | 服务端要么跑 `mock`（零密钥），要么由我们在服务端配好真实密钥 |
| C3 | **链接要活过评审期** | 9/26 提交 → 9/30 初赛公布 → 10/15 决赛 | 需要**至少 3 周**的稳定存活，且不能取决于某台个人电脑是否开机 |
| C4 | **仓库为 public，源码链接另交** | 已满足 | 在线链接只需"可访问可交互" |
| C5 | 服务端当前**不托管前端静态资源** | `apps/server/src` 无 `express.static` | 选定的载体决定 `P-C13` 怎么改 |

### 1.2 候选方案对比

| 方案 | 怎么部署 | 对 C3（存活） | 对 C1（要后端） | 代价 / 风险 |
|---|---|---|---|---|
| **A. 托管平台单服务**（Render / Railway / Fly 等长驻 Node） | 服务端同时托管前端 `dist`，一个进程一个域名 | ✅ 平台级存活 | ✅ 原生 Express，无需改造 | 免费档可能休眠（冷启动 30–60s，评委第一次点开会很慢）；部分平台要绑卡 |
| **B. Vercel / Netlify**（静态 + Serverless Functions） | 前端静态，`/api` 拆成 Serverless 函数 | ✅ 平台级存活 | ⚠️ **要改造**：Express 应用得包成函数（`api/` 或 `netlify/functions`），路由与中间件语义有差异 | 改造量最大的一条；且函数有执行时长上限，与"请求总预算 90 秒"叠加后要实测 |
| **C. 腾讯云**（CloudBase 云托管 / 轻量应用服务器） | 单服务托管前端 + 后端 | ✅ 国内访问最稳 | ✅ 长驻进程 | 需实名账号；轻量服务器按月计费；**域名访问国内需备案**（用平台默认域名或 IP 可绕过） |
| **D. 前端静态托管 + 本机服务 + 隧道**（cloudflared / ngrok） | 前端上静态托管，后端跑在本机，隧道暴露 | ❌ **要求本机连续开机 3 周**；免费隧道域名随机、可能变动 | ✅ 无需改造 | 成本最低、**最快**；但"本机是否一直开着"是不可接受的单点 |

### 1.3 **建议：A 或 C，二选一；不建议 B、D**

- **排除 D（隧道）**：它把"链接可用"绑到一台个人电脑的开机状态上。9/26–10/15 跨三周、
  含国庆假期，这个单点太脆；而且免费隧道换域名就等于换链接，提交后不可改。
- **排除 B（Vercel/Netlify）**：本项目是**单仓库、单 Web 服务**，服务端是长驻 Express
  （`dependencies` 含 `@tencent-ai/agent-sdk` 的 SDK 通道 + 会话/图谱的内存存储）。
  Serverless 化不仅要改造成本，**还会打断内存态**（会话、图谱、画像都放内存，
  实例冷启动/多实例下状态不共享）→ 与 `P-C13` 的"同源部署"目标背道而驰。
  **一句话：本项目不适合 Serverless。**
- **A 与 C 的差别只在"国内可访问性 vs 开通门槛"**：
  - 若**已有**腾讯云账号且不介意少量费用 → 选 **C**（国内评委访问最稳，且与"腾讯云"赛事语境一致）；
  - 若希望**零成本、今天就出链接** → 选 **A**（注意选不会休眠的档位，否则首次访问体验很差）。

### 1.4 无论选哪个，实现侧的活是同一批（`P-C13`）

1. 服务端增加静态托管（`express.static(webDist)` + SPA fallback），**同源**提供 `/` 与 `/api`；
2. 构建顺序改为 **先 web 后 server**（或让服务端从固定相对路径读 web 产物），并保证
   **web 产物缺失时服务端仍能启动**（否则会破坏 `verify:dist` 的产物自检 —— 那是 `B1` 的验收点）；
3. 更新 `verify:dist`：增加"静态首页可返回 200"的断言（让它覆盖部署形态，而不是只覆盖 API）；
4. `README` 启动说明补"生产形态启动方式"，并写明 `MODEL_PROVIDER` 取值与是否 mock；
5. 部署流程固定执行 `npm run verify:predeploy`（已就位）。

### 1.5 密钥与成本（C2 相关）

- **零成本路线**：线上跑 `MODEL_PROVIDER=mock`。**界面自带醒目标注**（页头横幅 + 每条回答的
  `mock 演示数据`），所以这不是"冒充真实能力"，而是**如实标注的演示通道**。
- **真实通道路线**：在平台侧配 `DEEPSEEK_API_KEY`。代价是**评委的每一次演示都会消耗我们的额度**，
  且无法限制用量。若走这条，建议同时设 `MODEL_TIMEOUT_MS` 与访问频次上的人为约束。
- **建议**：在线链接默认走 mock（零成本、零密钥、行为可预期），并在作品说明里写明
  "线上为演示通道，真实通道验收记录见仓库 changelog"。**这比"配了密钥但额度被刷爆"更稳。**

## 2 D3：模型通道选型（视觉 / 嵌入 / 语音）

### 2.1 现状

| 通道 | 状态 |
|---|---|
| `deepseek`（默认） | ✅ 已接入并实测（文字 1213 ms / 图片 3195 ms） |
| `sdk`（CodeBuddy Agent SDK） | ✅ 已接入并实测（文字 12–21 s / **图片 17.7 s**） |
| `mock` | ✅ 本地开发 |
| 视觉（结构化描述） | ⚠️ 通道支持图片调用，但 `/api/parse` 尚未接图片路径（`I6`） |
| 嵌入 | ❌ 未引入，且 V2.0 §5.1 已放宽为「不强制不用」，**初赛结论是不引** |
| 语音（ASR） | ❌ 未引入 |

### 2.2 建议

| 能力 | 建议 | 理由 |
|---|---|---|
| **视觉** | **复用已接入的两条通道**，不新增供应商 | 两条通道都已用真实密钥实测过**图片调用**（`docs/changelogs/2026-09-17-C-DS转为默认通道.md`），零新增集成成本；新增供应商只增加密钥管理与超时口径的复杂度 |
| **嵌入** | **不引入** | 初赛以轻量索引为主，图谱是概念级依赖而非语义检索；引入嵌入会带来向量库、维度、费用三件新事，收益不成立 |
| **语音** | **优先浏览器内置 Web Speech API；不达标再上云 ASR** | 零依赖、零成本、零密钥；缺点是要联网且中文识别质量一般。**但要注意**：它意味着"识别在浏览器侧发生"，需要在界面上如实说明，且**不能声称是服务端识别** |

### 2.3 语音的额外口径（与真实性红线相关）

若走浏览器 Web Speech API：
- `/api/parse` 的语音路径**依然是"未接入"**，界面必须**分开说明**：
  "语音在浏览器内转成文字后进入文本路径"≠"服务端具备语音识别能力"；
- 不能把这条写进 `P-B5 多模态解析` 的验收里当作已完成（`B5` 的验收是 6 份素材人工比对）。

## 4 我不做什么

- **不替负责人选载体**：A 与 C 的差别涉及账号、费用与备案，属于团队决定；
- **不在决策前实现 `P-C13`**：同源部署的做法**取决于载体**（长驻服务 vs Serverless，
  见 §1.3 —— 而本项目的内存态明确排除了 Serverless）。先决定，再实现，避免做一半推翻。
