## 一、赛事方原话（合规依据）

> **「本次赛事以腾讯 LearnBuddy 平台为载体，最终效果呈现时最好不要包含第三方 AI」**

这句话有三层约束，逐层拆开：

| 原话 | 约束范围 | 对本项目的要求 |
|---|---|---|
| "以腾讯 LearnBuddy 平台**为载体**" | 作品底座 | **主通道必须是 LearnBuddy** |
| "**最终效果呈现时**" | 演示、评委体验的那一刻 | 开发与本地调试不在此列 |
| "**最好不要**包含第三方 AI" | 强烈建议，非绝对禁止 | 应默认不启用，且启用时必须可见 |

**关键在"最好不要"这三个字** —— 它比"禁止"松，但仍足以决定：**第三方通道不能出现在呈现路径上。**

## 二、两条通道

| | 主通道 | 备选通道 |
|---|---|---|
| 实现 | CodeBuddy Agent SDK（`@tencent-ai/agent-sdk`） | DeepSeek `/chat/completions` |
| 认证 | `CODEBUDDY_API_KEY` + `CODEBUDDY_INTERNET_ENVIRONMENT=internal` | `DEEPSEEK_API_KEY` |
| 模型名 | **由上游动态分配，只能回读** | 由 `DEEPSEEK_MODEL` 指定（当前填 `deepseek-flash`） |
| 图片 | **已实测通过** | 已实现，**未实测** |
| 合规 | ✅ 主路 | ⚠️ 最终呈现不得启用 |
| 启用方式 | `MODEL_PROVIDER=auto`（默认）或 `=sdk` | `MODEL_PROVIDER=deepseek` |

适配器实现分别在 `apps/server/src/model/workbuddy.ts`（主）与 `deepseek.ts`（备选），
两者实现同一个 `ModelAdapter` 接口，因此**教学模块与接口层完全不知道走的是哪条通道**。

## 三、三条硬性约束（本次实现的核心）

### 1. 默认不可达

备选通道**只有**显式设置 `MODEL_PROVIDER=deepseek` 才会启用。
`auto` 档位永远不会走到它（`auto` 只有两种结果：有主通道密钥走 sdk，无密钥走 mock）。

### 2. 不参与自动降级

**主通道失败时绝不自动切到备选通道。**

理由不是偏好，是规则：**自动降级恰好发生在"要呈现给评委"的那一刻** ——
主通道一旦在演示现场失败，自动降级会让一条不允许出现的通道静默接管，
正好撞在第一节的约束上。

此外还有两个技术理由：
- 两条通道的回答风格与质量不同，中途静默切换会让演示结果不可复现；
- 现场无法解释"这条回答是谁给的"，评委追问时答不上来。

**因此「演示不能中断」这个需求改由其他方式满足**：提前预热、手动切换并当众说明、
本地演示＋录屏兜底。**不用自动降级去满足它。**

### 3. 启用时必须可见

走备选通道时，启动日志打印醒目警告，且 `GET /api/health` 如实报告。实测输出：

```
[server] ⚠️ model=deepseek（第三方通道）—— 赛事方要求最终效果呈现不包含第三方 AI，请勿在演示或评委体验时启用
[server] ⚠️ 已选择备选通道但未配置 DEEPSEEK_API_KEY，调用会直接失败。

GET /api/health  →  {"ok":true,"version":"0.1.0","modelProvider":"deepseek","mock":false}
```

**设计目标**：无论规则后续如何解读，这套代码都是安全的 —— 它不会自己启动，启动时会喊出来。

## 四、一个推论：mock 同样不能作为最终呈现

按"最终效果呈现"这个尺度，**mock 也不合格**。

mock 返回的是预置假数据。它不是"第三方 AI"，但它**同样不是 LearnBuddy 的真实能力** ——
说明书 9.2 那条诚实性要求正是管这个的。

**演示前必须做一次检查**：`GET /api/health` 要报出 `"mock": false`。

## 五、`MODEL_PROVIDER` 四档行为表

| 值 | 主通道密钥 | 实际通道 | 说明 |
|---|---|---|---|
| `auto`（默认） | 有 | `sdk` | 推荐设置 |
| `auto` | 无 | `mock` | 让 A 无密钥独立开发（说明书 8.2）。降级结果会如实报告，不是"静默降级" |
| `mock` | — | `mock` | 强制假数据 |
| `sdk` | 有 | `sdk` | 强制主通道 |
| `sdk` | 无 | `sdk` | **不静默降级**，启动时警告"调用会失败" |
| `deepseek` | — | `deepseek` | 备选通道，启动时打印合规警告 |

**唯一的隐式行为是 `auto` 无主通道密钥时走 mock**，且该结果通过启动日志与 `/api/health` 对外可见。

## 六、实测验证（2026-09-17）

| 验证项 | 结果 |
|---|---|
| 四个档位的通道推导 | **全部正确**（`auto`→sdk、`mock`→mock、`sdk`→sdk、`deepseek`→deepseek） |
| 备选通道无密钥时 | 正确返回 `AUTH`：`缺少 DEEPSEEK_API_KEY…`，**不消耗任何额度** |
| 启动警告 | 走 `deepseek` 时两条警告均打印 |
| `/api/health` 报告 | `modelProvider=deepseek`、`mock=false`，如实 |
| 接口冒烟（29 项） | **全部通过**（用新代码、新起的服务跑，非旧进程） |
| 主通道真实调用 | **通过**，模型 `hy4-preview-f`，21.4 秒 |
| 四个 workspace 类型检查 | 零错误 |

**过程中发现并修正的一处操作失误**：第一次跑接口冒烟时服务端口被上一次测试的遗留进程占用，
新服务启动失败（`EADDRINUSE`），而那 29 项其实是打到了**旧代码**上。
已清理进程后**用新代码重跑**，结论以第二次为准。如实记录，避免把无效验证当成有效。

## 七、待验证项

1. **备选通道的真实调用未实测** —— 尚无 `DEEPSEEK_API_KEY`。需要验证：
   ① 能否调通；② `deepseek-flash` 是否为支持图片的型号；③ 图片的 data URI 格式是否被接受。
2. **图片格式按 OpenAI 兼容惯例实现，未实测**。若上游返回格式错误，
   只需改 `deepseek.ts` 的 `toMessages()` 一处（约 5 行）。
3. **未使用 DeepSeek 原生的 `response_format: json_object`** ——
   有意为之：两条通道对 B 的行为应一致，而主通道无法使用该字段（上游不兑现）。
   若将来确认 DS 该字段稳定，可单独为备选通道启用，但需同步更新本记录。
