## 2. 为什么新增一个接口，而不是复用 `POST /api/profile`

`POST /api/profile` 是**通用的事件投递口**：调用方说什么事件就记什么事件。
而提交练习要做的事性质不同 —— 服务端要**按 `itemId` 反查题库**才能判分与归因，
也就是**端点本身要参与领域判断**。把这段逻辑塞进事件投递口，
会让"画像能记什么"取决于"投递口会算算什么"，**两边都说不清**。

## 3. ① ② `POST /api/quiz/attempt` 与归因类型

### 3.1 具体定义（照录）

```ts
/** packages/contracts/src/quiz.ts */
export type AttributionBasis =
  | 'option-tag'         // ① 干扰项预标注：理由就是那条人工写下的标注，逐条可查（最强）
  | 'structural'         // ② 结构推导：所选与正确选项的集合关系（一次可复算的包含判定）
  | 'diagnostic-agent';  // ③ 诊断 Agent（模型）—— ⛔ 见 §3.3，本层**未实现**

export interface QuizAttribution {
  kind: MisconceptionKind;
  pattern: string;        // 画像「常见误区」的累计键（跨题稳定）
  reason: string;         // 可核对理由：必须指向题目里的具体一处
  basis: AttributionBasis;
  evidence: {             // 核对材料：选中的与正确的两侧原文
    selectedOptionId: string; selectedText: string;
    correctOptionId: string;  correctText: string;
  };
  verification: VerificationStatus;  // ①→human ②→symbolic ③→unverified
}

export interface QuizAttemptAnswer { itemId: string; selectedOptionId: string; }
export interface QuizAttemptRequest { sessionId: string; answers: QuizAttemptAnswer[]; }
export interface QuizAttemptResult { itemId: string; correct: boolean; attribution: QuizAttribution | null; }
export interface QuizAttemptResponse {
  results: QuizAttemptResult[];
  profile: LearnerProfile;
  unattributed: number;   // 本批「答错但没能归因」的题数
}
```

### 3.2 四条写进契约注释的口径（**别回退**）

1. **`evidence` 是必需的，不是可选的。**
   §2.6 要求「不得仅凭答案对错断言」。`evidence` 把**核对所需的两侧原文**一起带上 ——
   学生与复核者**不需要相信归因**，可以当场拿这两句自己比一遍。
   ⇒ **没有能力提供 `evidence` 的实现，就不该返回归因，而应返回 `null`。**

2. **`pattern` 必须是**定值**，不能是从 `reason` 里摘出来的摘要。**
   画像要做**跨题累计**，需要一个**跨题稳定**的键。`reason` 是逐题句子（含具体数字与点），
   天然不可能跨题相同；自动摘要摘歪了会把两个坑并成一个、或把一个坑裂成两个 ——
   **两种错误都看不出来**。⇒ 短名字与 `reason` 一样由出题人写下，
   且**同一类错误在相关题目上复用同一个词**（`fx-tan-1:A` 与 `fx-tan-3:A` 都是「把函数值当导数值」）。

3. **请求只送 `itemId` + 选中项 id，不送题干与选项正文。**
   让客户端把"正确答案是什么"一起送上来，等于**把判分与归因的依据交给被评估方**。
   正确答案由**服务端**按 `itemId` 从题库取 ⇒ 判分与归因**同源**，不存在"判对了却归错了题"。
   **代价如实记下**：按材料／变式生成的题不在题库里 ⇒ 一律归因 `null` 并计入 `unattributed`。
   **这是如实的结果，不是缺陷。**

4. **`attribution === null` 有**两种**含义，界面必须分开说：**
   - **答对了**（归因只描述"错在哪"，对正确作答没有可说的）；
   - **答错了但推不出** —— 此时应如实讲"无法归因"。
   把后一种说成"你已经掌握"是失真（§2.6）。
   `unattributed` **单独回报**而不是让前端自己数：前端只知道 `null`，**分不清这两种**。

### 3.3 ⛔ `diagnostic-agent` 这个取值**保留在类型里，但没有实现**

**这不是"预留待做"，是一处必须解释的不一致。**

- **保留的理由**：`AttributionBasis` 是一个**如实回报"理由有多可核对"**的字段。
  如果将来真有人接了第三层，**必须**有一个取值把它标成"最弱" ——
  删掉这个取值，后来者就只能把它谎报成 `structural`。
  保留它，等于**把"这一层最弱"这件事写死在类型里**。
- **不实现的理由**：`P-B9` 的判据是"须给出**可核对**理由"。**模型给的理由不可核对**，
  与判据直接冲突（否决过程见 `reviews/2026-09-24-B-教学能力补全复核.md` §二 R2）。
- **因此当前的 `ATTRIBUTABLE_KINDS` 只由层 ①② 产出**，
  断言里有一条专门锁"没有任何归因的 `basis` 为 `diagnostic-agent`"。

> **如果后来者想接第三层**：请先回答"它的理由怎样才能被学生当场核对"。
> 答不上来就别接 —— 那正是这条待办要防的东西。

## 4. ③ ④ `AgentDegradation` 与 `TutorResponse.degraded`

### 4.1 具体定义（照录）

```ts
/** packages/contracts/src/agents.ts —— 新文件 */
export type AgentRole = 'tutor' | 'verifier' | 'diagnoser' | 'quizzer';
export const AGENT_LABELS: Record<AgentRole, string> =
  { tutor: '答疑', verifier: '验证', diagnoser: '诊断', quizzer: '出题' };

export interface AgentDegradation {
  agent: AgentRole;
  reason: string;    // 哪个 Agent 没跑成（固定句子，**不含**上游报错原文）
  fallback: string;  // 降级后**实际发生了什么**
}
```

```ts
/** packages/contracts/src/tutor.ts */
export interface TutorResponse {
  /* …既有字段不变… */
  degraded?: AgentDegradation[];   // 加性可选
}
```

### 4.2 为什么这些类型放在 `packages/contracts`，而不是只留在 `@lc/teaching`

降级记录要**穿过接口**到达界面：**服务端产出它、响应体带着它、面板显示它**。
三处都要认得同一个形状 —— 若只在教学包内部定义、由服务端各写一份，
就会出现"契约说三个字段、实现给了四个"的**漂移**，
而这种漂移是**静默的**（多出来的字段没人读，少掉的字段没人报错）。

依赖方向 `teaching → contracts`（`@lc/teaching` 从本包引入并原样再导出），
与 `MisconceptionKind` 等既有类型一致，**不构成循环依赖**。

### 4.3 三条口径

1. **主 Agent 失败 ⇒ 整条请求失败**（如实报错，**不假装答了**）；
   辅助 Agent 失败 ⇒ 只记一条 `degraded[]`，**主流程照常返回**。
2. **`fallback` 写"实际发生了什么"，不写"已降级"。**
   学生要能据此判断"这次的答案还差什么"（如"这一版未经符号验证"）。
3. **`reason` 用固定句子，不含上游报错原文。**
   上游报错可能带模型通道的内部信息，**不该出现在面向学生的响应体里**；
   需要排查时看服务端日志，不靠响应体。

### 4.4 与既有 `droppedBlocks` 的分工（两个字段都在，别混）

| 字段 | 说的是 | 出现时机 |
|---|---|---|
| `droppedBlocks`（`I14`） | 这次**少了几块** | **仅在"部分被丢弃"时**；全被拒直接 403 |
| `degraded`（`P-B8`） | 这次**有哪一环没跑成** | 辅助 Agent 失败时 |

**两者都只在异常时出现**，界面须**分别如实说明**（E18：不得静默）。
只加字段而不渲染，等于**换个地方继续静默** —— 这是 `I14` 已经付过一次的教训。

## 5. 补记：三项**已完成但缺契约记录**的加性变更

> 而它们在 `docs/` 里**一处都没有登记**。

### 5.1 ⑥ `QuizSource` 加 `'variant'`、`QuizRequest.conceptIds?`（`P-B17`／**PR #27**，merge `4d242035`）

- **`QuizSource` 加 `'variant'`** —— 出题此前只有「项目自编 `fixed`」与「按材料 `material`」两条路。
- **`QuizRequest` 加可选 `conceptIds?: string[]`** —— 留出"我只想练这一条"的口子。
- ⚠️ **写进契约注释的关键一条**：`variant` 与另两者的差别**不在"谁出的"，
  而在出题依据是个人画像** ⇒ **题目本身不得暴露个人数据**
  （不写"因为你答错过"这类话；提示词第 4 条要求"读起来应当是一道普通的练习题"）。
- 相关纪律：**`source: 'variant'` 由服务端强制写入、不由模型自报**；
  前端 `QUIZ_SOURCE_LABELS.variant` 写「针对需加强的概念」，**不写"你的薄弱点"**。

### 5.2 ⑦ `GapResponse.corrected?`（`P-B2`／**PR #26**，merge `ab2cb9fe`）

- 语义：第一次生成未通过符号验证 ⇒ 把失败原因回喂模型**再生成一次** ⇒ 返回的是第二次的结果。
- **字段缺席表示"没走过重试"**，**不是**"保证没错"的意思（契约注释里写明）。
- 配套的口径在 `P-B2` 的实现里：**只修一次**；**不隐藏第一次的失败**（带 `firstFailure` 回去）；
  **重试过 ≠ 通过**（两次都 `failed` 就还是 `failed`，照常落 `DISPUTED`）。

### 5.3 补记里**没有**发现破坏性变更

三项都是**加性**：新增可选字段／新增枚举取值。既有消费方不传即不受影响。
