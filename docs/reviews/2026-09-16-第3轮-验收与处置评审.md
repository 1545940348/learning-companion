### 3. 实测推翻：C 判断"结构化输出支持"

**C 原判断**：SDK 导出 `OutputFormat` / `JsonSchemaOutputFormat` 类型且有 `Options.outputFormat`
字段，因此结构化输出可用，B 的校验可从"解析自由文本"降级为"校验已结构化字段"。

**推翻依据**：两次实际调用（`glm-5.3` 与 `minimax-m3`），
`ResultMessage.structured_output` 均未返回，模型照旧输出 markdown，enum 取值不受约束。

**处理**：`docs/tech` 第四章改写为"一次被实测推翻的判断"，保留原判断与推翻过程，
**不作事后美化**。结论同步给 B：不能依赖 `structured_output`。

**教训**：**SDK 暴露的类型能力，不等于上游服务会兑现。** 判断外部依赖能力必须以实际调用为准，
不能以类型定义或文档为依据。

### 4. C 的指令缺陷导致用户误操作（密钥误置）

**C 的原话**："把密钥填进 `D:\AI_Coding_Competition\.env`"。

**缺陷**：当时 `.env` **并不存在**，仓库中只有 `.env.example`。用户找到的只有那一个文件，
于是把真实密钥填进了**会被提交的文件**。

**人工判断**：这是 C 的指令不完整，不是用户的失误。

**处理**：完成处置与核查（结论：密钥从未进入 git 历史，无需更换）；
教训写入记忆：**给非技术用户下密钥指令前，先确认目标文件已存在或代为创建**。

**另一条经验**：处置顺序必须是"先清空受影响文件、后读取"，
因为**对话记录本身是参赛提交材料**，先读取会把密钥带进提交物。
