## 二、被否决或被修改的内容（关键记录）

### 1. 用户指示"以我的代码为准"被 C 修正

**用户原指示**：「跟我冲突的部分还有由我负责的部分就以我的代码为准」。

**C 的核对结果**：在 `packages/contracts` 上，五接口契约（`session`/`knowledge`/`tutor`/`quiz`/`api`）
**C 方是空的**，而它被 **12 处** import 依赖（A 的前端 3 处、B 的教学模块 4 处、服务端 2 处 + 包名声明）。
按"以我为准"执行等于删除这些文件，连带打断 A 与 B 的代码。

**C 的判断**：在"我有代码"的地方以我为准成立；在"我这边为空"的地方，"以我为准"等于删代码，
肯定不是用户本意。因此提出改为合并，并逐项列出归属。

**人工判断**：采纳 C 的修正。用户的指示改为「按合并方式执行，同时改 B 的接口」。

**这条记录的意义**：这是本轮唯一一次 C 未按字面执行用户指示、而是先说明风险再执行的情形。
按 8.4 留痕。

### 2. C 的工具链被队友方案取代

**C 原方案**：根 `tsconfig.json` 项目引用 ＋ `tsc -b` ＋ 各包 `dist` 产物。
**队友方案**：`tsconfig.base.json` 用 `moduleResolution: Bundler` ＋ `noEmit: true`，
各端用 `tsx`（开发）/ `tsup`（服务端构建）/ `vite`（前端）。

**两者不兼容**：`composite` 与 `noEmit` 冲突；`NodeNext` 与 `Bundler` 解析策略不同。

**判断**：保留队友方案。理由：它覆盖三端且提供 dev/build/start 完整脚本，
而 C 的方案只解决 C 自己的两个包。

**C 撤除的产物**：根 `tsconfig.json`、`packages/contracts` 的 `dist` 目录构建，以及过期的构建产物。
**记录为"被修改"，不是被否决**——为避免误解，特此说明取舍依据是覆盖面而非质量。

### 3. C 的包名 `@calc/*` 改为 `@lc/*`

队友已建立 `@lc/contracts`、`@lc/teaching`、`@lc/server`、`@lc/web` 四个包名并被多处引用。
C 的 `@calc/contracts` 仅存在于自己的两个文件里。

**判断**：采用队友命名，C 侧文件全部替换。理由：改名成本单向——改 C 的 4 处引用 vs 改队友的 12 处。

### 4. C 的根 `.env.example` 被队友的 `apps/server/.env.example` 取代

**取舍**：位置用队友的（服务端专属配置放在服务端目录更合理），
**内容用 C 的**（SDK 认证方式、密钥警示、无 BASE_URL 说明）。

### 5. 队友的 HTTP 直连适配器被替换

**队友实现**：`fetch(\`${MODEL_BASE_URL}/chat/completions\`)`，配 `MODEL_PROVIDER`/
`MODEL_API_KEY`/`MODEL_BASE_URL`/`MODEL_NAME`。

**替换依据**（均为实测，非偏好）：
- 本接入方式**没有 base URL**，认证由 SDK 读取环境变量完成；
- **没有固定模型名**，模型由上游动态分配，同日实测出现五个不同型号；
- 用户曾明确指示「不要猜测原始 HTTP 地址或套用普通聊天接口」。

**但保留其 mock**：`MODEL_PROVIDER=mock` 的机制被保留并扩展为
`auto` / `mock` / `sdk` 三档。其中 `sdk` 档位是 C 新增的：无密钥时不静默降级，
用于防止演示或截图时误把 mock 当成真实能力（说明书 9.2 诚实性要求）。
