## 三、问题清单

### P1 —（建议合并前修复）

**P1-1｜同一个 `SESSION_STALE` 有两副面孔，且入口那副是不可重试的**
`apps/server/src/http/routes.ts:383-389`

`errorHandler` 的 `ApiError` 分支把 `retryable` **硬编码为 `false`**，而本次新加的 `SessionVersionConflictError` 分支（:402-408）返回 `409 / retryable: true`。两者是同一个契约错误码，实测行为不一致：

| 触发位置 | 实测结果 |
|---|---|
| `assertVersion` 入口校验（`/tutor`、`/gap`） | **400** `SESSION_STALE` **retryable:false** |
| `commitMaterials` / `commitSupplement` 提交复核（本次新增） | **409** `SESSION_STALE` **retryable:true** |

前端 `apps/web/src/api.ts:45` 读的正是 `retryable`（`?? false`）。因此"基于最新状态重试"这条说明书 5.3 的要求，在入口路径上会被前端判为不可重试，**没有"一键重试"给到学生**。

PR 描述已把此条列入"仍待处理"，但它是本 PR 新增半边行为之后才产生的分叉。建议本 PR 内一并收口：让 `retryable` 由错误码推导，而不是在分支里写死。

**P1-2｜未分类的服务器内部错误被标成"可重试"**
`apps/server/src/http/routes.ts:422-435`

兜底分支无论 `INTERNAL` 还是超时，一律 `retryable: true`。实测：

```
POST /api/knowledge  {"materials":"abc"}   → 500 {"code":"INTERNAL","retryable":true}
POST /api/tutor      body = '{bad json'    → 500 {"code":"INTERNAL","retryable":true}
```

两处都有问题：
- 畸形 JSON 属**客户端**错误，应回 **400 `BAD_REQUEST`**，而非 500；
- `INTERNAL` 意味着我们有 bug，让前端给学生"一键重试"是误导 —— 这恰好违背本 PR 要达成的目标（"让前端据此给出不同的下一步"）。

与 P1-1 同一函数、同一处修复。

**P1-3｜轻路径只要"省略"`sessionId` 字段就会被判为越权内容**
`apps/server/src/http/routes.ts:250-252`

```ts
requireAuthorization: body.sessionId !== null,
```

`sessionId` 显式传 `null` 时该表达式为 `false`（轻路径，正确）；但**字段被省略**时 `body.sessionId` 是 `undefined`，`undefined !== null` 为 `true`，于是零材料提问被当成"需要授权"。实测：

| 请求 | 实测结果 |
|---|---|
| `{question, sessionId: null}` | 200，`sourceType: "ai-supplement"`，`basedOnMaterial: false` ✅ |
| `{question}`（省略字段） | **400 `UNAUTHORIZED_CONTENT`「AI 补充内容未经学生授权」** ❌ |

说明书 V1.4 §5.2 写的约定是"轻路径调用约定为 `sessionId:null`"，所以严格照约定实现的前端不会踩到；但省略字段是最自然的 JSON 写法，一旦踩到，报错文案指向"内容授权"，与真实原因（缺省值判定）完全对不上，排查成本很高。建议改为 `Boolean(body.sessionId)`。

> 该行是既有代码，本 PR 未改动；但 V1.4 把轻路径列为核心路径，且修复只需一行，建议本轮顺手修掉。

### P2 —（可合并，但应排期）

**P2-1｜请求体没有形状校验，内部报错原文直接回给客户端**
`apps/server/src/http/routes.ts:190`（`body.materials ?? []` 之后直接当数组用）

实测 `{"materials":"abc"}` 与 `{"materials":[{"id":"x"}]}` 都返回
`500 INTERNAL：Cannot read properties of undefined (reading 'length')`。
既暴露了实现细节，又让"坏 JSON 不得返回成功答案"以外的场景（无效结构）落到未分类分支。V1.4 §9.3 把"字段校验"列为待办，本 PR 未接。建议加一层最小形状校验（哪怕是手写守卫）。

**P2-2｜`deepseek.ts` 丢弃 `error.cause`，云端排障会失效**
`apps/server/src/model/deepseek.ts:142`

`redact(error, …)` 走的是 `String(error)`。Node 的 `fetch` 只抛 `TypeError: fetch failed`，真正原因（`ENOTFOUND` / 证书 / `ECONNREFUSED` / 代理）在 `error.cause` 上。实测 `smoke:model:deepseek` 指向不可达地址时，`detail` 只有：

```
"detail": "TypeError: fetch failed"
```

V1.4 把"云端独立验证"列为唯一挡住交付的事项，而云端最常见的失败恰恰是 DNS/证书/出网策略 —— 按现在的写法，云端失败时拿不到可用信息。建议补 `error.cause` 后再 redact。

**P2-3｜响应里的 `model` 与 `usage` 被丢弃，与说明书 5.2 不一致**
`apps/server/src/model/deepseek.ts:129-136`

适配器只取 `data.choices[0].message.content`。`deepseek.ts` 头部注释据此写成"响应不带模型型号回显，故不提供实际型号回读"，但说明书 V1.4 §5.2 的要求是"`DEEPSEEK_MODEL` 须填写真实可用型号，**返回值可用时记录实际型号**"。免鉴权复核方式：我用本地假上游按 OpenAI 兼容格式返回了 `model` 与 `usage`，两者均被静默丢弃，日志中无从体现。

代价：`DEEPSEEK_MODEL` 若被置成一个网关会"照收不误"的名字，无法从日志发现；token 用量也没有留痕，而 V1.4 要求"记录真实耗时"、额度也需要确认。建议至少把 `model` 与 `usage` 打进 `model.call.ok` 日志字段。

**P2-4｜3 个代码提交没有对应的 `plans/` 与 `reviews/`**
按项目硬性约定（`plans/` 每轮开始前、`reviews/` 每轮结束后，且与该轮对话一一对应），本 PR 的 6 个提交中：

- 3 个代码提交（`6a76f62`、`ea4f702`、`82866a6`）各有一份 changelog ✅，但**无对应 plan**；
- `docs/plans/2026-09-17-C-方案V1.4-DS主通道.md` 明写"范围：仅 docs 中的方案正本…**不改代码／密钥，不实测收费接口**"；
- `docs/reviews/` 里两份 9-17 评审也都只覆盖**只改文档的那两轮**。

结果是：真正改代码、真发起了收费调用的那一轮，在 `plans/` 与 `reviews/` 两类里都留空了。另外 `docs/tech/2026-09-17-C-DS主通道与展示边界.md` 写"本轮不修改上述代码，不读取密钥，不发起外部调用"，与同一 PR 内的 changelog（真实密钥实测、1.2 s 耗时）在同一份 PR 里互相矛盾。PR 描述用"前三个是历史轨迹，一并带入以便决策链完整可溯源"作了解释，这个处理可以接受，**但需要在 `docs/` 里补一句显式的版本指向**，否则评委读到两份互相否定的技术记录时会先怀疑真实性，而这正是本项目最想守住的资产。
