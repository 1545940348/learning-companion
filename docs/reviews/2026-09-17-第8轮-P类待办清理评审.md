## 2 被否决 / 被修改的真实记录

### 2.1 ✗ **我自己写的检查脚本，第一版有两处假阳性（被自己的运行结果打回）**

`check-sensitive.mjs` v1 跑出来第一句话就是 `[失败] 存在禁止入库的被跟踪路径 —— apps/server/.env.example`。
两处都是我的规则写错了：

| 我的写法 | 错在哪 | 改成 |
|---|---|---|
| `/(^|\/)\.env\.[^/]+$/` 判定禁止路径 | `.env.example` 是 `.gitignore` 里**明确放行**的例外，被误判成"密钥文件变体" | 加**例外名单**，并把"例外生效"也做成一条通过项（防止例外本身失效） |
| `(?:API[_-]?KEY\|…)\s*=\s*["']?[A-Za-z0-9_\-]{12,}` | `\s*` **跨行匹配**：`DEEPSEEK_API_KEY=`（空值）后面紧跟的下一行变量名被吃掉，于是"空值"被判成"有值" | 改为 `[ \t]*`（只允许行内空白），并在注释里写明**为什么不能用 `\s`** |

**教训**：正则里的 `\s` 在"逐行读取配置"的场景下几乎总是错的 —— 它会越过行边界。

### 2.2 ✗ **历史扫描方案被工具打回一次，整体重做**

- **我的第一方案**：用 `git grep -E '<所有模式用 | 连接>' $(git rev-list --all)` 扫全部提交。
- **实际**：git 报 `fatal: command line, '...': Invalid preceding regular expression` ——
  **`git grep -E` 走 POSIX ERE，不支持 `(?:…)` 非捕获组**（`\s` 也是 GNU 扩展，不可移植）。
- **如果只修正则**：工作区扫描用 JS RegExp、历史扫描用 POSIX ERE，就变成**两套规则**；
  两套必然漂移，而**"历史扫描悄悄失效"是最危险的一种失效** —— 它给出的是虚假的安全感。
- **重做**：改用 `git cat-file --batch` 把全部 blob 取到 Node 里扫，**工作区与历史共用同一套规则**。
  副产物是可读性更好：报告能直接说"扫了 245 个 blob"。

### 2.3 ✗ **依赖核对脚本的解析 bug：把作用域包切成了两半**

- **我的写法**：README 表格的包名单元格按裸 `/` 切分（为了支持 `` `react` / `react-dom` `` 这种多包写法）。
- **实际**：`@tencent-ai/agent-sdk` 被切成 `@tencent-ai` 与 `agent-sdk` 两个不存在的包，
  于是报出 ["代码里用了但 README 未声明"] 与 ["README 声明了但代码里没有"] **两条假失败**。
- **改成**：只按**两侧有空格的斜杠**切（`/\s+\/\s+/`），并在代码注释里写明这个坑。

### 2.4 ✗ **一起我自己造成的构建事故（本轮最严重的一次返工）**

- **我做了什么**：为了修 `concurrently` 未声明，执行 `npm install --save-dev concurrently`。
- **出了什么**：npm 收尾被系统拒绝（`EPERM` 于 `package-lock.json`），随后 safe-delete 钩子
  `ETIMEDOUT`；**而它中途已经删掉了 `@rollup/rollup-win32-x64-msvc`** → `npm run build` 直接挂。
  后续两次 `npm install` 都失败，`@rollup` 目录被清空。
- **根因**：锁文件里**没有** rollup 平台包条目 → npm 把已装的平台包当 extraneous 删除；
  删完之后自己失败，于是处于"删了没装"的中间态。
- **我否决的修法**：
  - ✗ 手改 `package-lock.json`：需要完整传递依赖树与 integrity 哈希，**改一半比不同步更糟**；
  - ✗ 自研 dev 启动器替掉 `concurrently`：把"依赖声明问题"换成"进程管理问题"，**用一个新问题换旧问题**；
  - ✗ `npm install -g` / 换包管理器：环境不允许。
- **实际修法**：绕开 npm —— 按 `node_modules/rollup/package.json` 的版本号从 registry 下载 tgz，
  用 Python `tarfile` 解压到目标目录（**全程无删除**）。已恢复并重新构建通过。
- **教训（已写进 `知识库.md` §13.4）**：**在这台机器上动依赖前，先确认失败会不会造成"删了没装"**。
  本次之所以踩到，是因为我按"标准做法"执行了一条**在这里不标准**的命令。

### 2.5 ⚠️ **一次差点发生的误报：读到了旧日志**

`npm run verify:dist > _vd.log` 报 `/usr/bin/bash: line 1: _vd.log: Permission denied` ——
**重定向失败意味着命令根本没执行**，而我紧接着 `grep` 拿到的却是**上一次**的输出
（8 项通过）。差点把旧结果当新结果报上去（实际是 11 项）。

- **发现方式**：日志文件时间戳与项数对不上（我预期 dist 是 11 项）。
- **处置**：改用不重复的日志名重跑，并把这条坑写进 `知识库.md` §13.4：
  **每轮用不重复的日志名，读结果前先确认时间戳**。

### 2.6 ⚠️ **新的敏感检查脚本立刻抓到了我自己上一轮的失误**

脚本报 `[注意] 工作区出现个人邮箱` —— 命中的是**我上一轮写的两个文档**：
记录 `B2` 决策时，我把队友的 QQ 邮箱**明文写进了 changelog 与 todo.md**。

- **为什么这算失误**：当时负责人决定的是"**照转、不重写 git 历史**"，
  而我把该邮箱写进正文，等于把暴露面从「git 元数据（要 `git log` 才看到）」
  升级为「文档正文（可被搜索、可直接读到）」——**是对当事人不利的主动放大**。
- **处置**：两处改为"**事实照记，标识符不录**"（写"一条队友的 QQ 邮箱"，不写具体地址），
  并在被修改的 changelog 里**留下说明**（§6.2 加了一段"本节原先明文写出，已于第 8 轮删除"），
  不做静默改写。
- **诚实边界**：历史提交里仍留有那两处明文（已推送）。这是**负责人已决定的"不重写历史"**的代价，
  脚本把它报为 `[注意]` 而非 `[失败]`，正是为了区分"工作区问题（要修）"与"历史问题（已决定不修）"。
