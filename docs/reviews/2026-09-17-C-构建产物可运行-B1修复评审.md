## 1 被否决的方案（全部为实测否决，非推测）

### R1（否决）`tsup --no-external` —— CLI 根本不支持该参数

- **AI 原始判断**：tsup 的配置项里有 `noExternal`，CLI 上应该也能写成 `--no-external <pkg>`。
  并据此直接给出了修复命令。
- **实测**：`npx tsup --no-external @lc/contracts` 报
  `` CACError: option `--external <name>` value is missing ``。
  查 `npx tsup --help`：只列出 `--external <name>`，**没有 `--no-external`**。
- **教训**：把配置项名直接套到 CLI 上是猜测。**先看 `--help` 再写命令**，成本 1 秒。

### R2（否决）用 `tsup.config.ts` 写 `noExternal`

- **AI 原始判断**：CLI 不行就走配置文件，这是标准做法。
- **实测**：构建失败 —— safe-delete 钩子拦住 tsup 通过 `bundle-require` 生成并删除的
  临时配置文件 `tsup.config.bundled_5t1nlyp6n4.mjs`。
- **处置**：换成 `.mjs` 再试一次。

### R3（否决）换成 `tsup.config.mjs` 绕过临时文件的产生

- **AI 原始假设**：纯 `.mjs`、无 import 的配置对象，`bundle-require` 应该能直接读取，
  不必打包成临时文件。
- **实测**：**同样失败**，临时文件改为 `tsup.config.bundled_mmo0x0x0n68.mjs`。
  `bundle-require` 对任何配置文件都走"打包 → 读取 → 删除"三步，与文件类型无关。
- **结论**：**本环境中任何 tsup 配置文件都不可用**，与配置内容无关。
  这条路彻底封死，转向"不依赖配置文件"的方案。

## 2 一处验证方法本身的错误（比方案错误更值得记）

### R4（修正）差点因为"grep 不到中文"判定内联失败

- **AI 原始判断**：`grep -c "项目自编练习" dist/index.js` 返回 `0`，
  于是判断"教学模块没有被内联，修复无效"。
- **实际情况**：`esbuild` 的默认 `charset` 是 **`ascii`**，会把所有非 ASCII 字符
  **转义为 `\uXXXX`**。所以产物里 `项目自编练习` 变成了
  `\u9879\u76EE\u81EA\u7F16\u7EC3\u4E60`，**grep 中文必然为 0**。
  同一文件里 ASCII 的 `fx-der-1` 能匹配到 —— 这个反差本应立即引起怀疑。
- **改用正确的探针后**：产物头部可直接看到 `// ../../packages/contracts/src/session.ts`
  等内联段，`analyzeKnowledge` / `supplementGap` 各出现 3 次。
- **教训**：**用产物里"中文被转义"这一特性去 grep 中文，是必然失败的探针。**
  验证内联应看 ① 产物的 import 列表 ② 内联段的路径注释 ③ ASCII 标识符。
  差一点据此推翻一个正确方案 —— 这是"验证手段不当导致误判"的典型案例。

### R5（修正）背景进程与端口冲突造成的一次误读

- **现象**：`verify:dist` 一度报"找不到构建产物"，但同时 `grep` 能读到该文件。
- **原因**：上一条命令把进程放到后台并重定向日志，前一次失败运行留下的日志与端口占用
  （3000 被上一轮的演示服务占着）叠加，使得现象难以归因。
- **处置**：改用独立端口（3010）与独立日志，一次只验证一件事，问题消失。
- **教训**：多个后台进程 + 复用端口 + 复用日志文件名，会让"证据"互相污染。
  验证部署形态时应**固定用独立端口、独立日志**。
