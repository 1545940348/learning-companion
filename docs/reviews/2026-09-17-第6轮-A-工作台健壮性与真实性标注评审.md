## 1 发现的真实缺陷（写代码时撞见的，不是事后复盘）

### R1（缺陷）忙碌态是单值，两个动作会互相覆盖状态

- **原有实现**：`busy: null | 'knowledge' | 'gap' | 'tutor' | 'quiz' | 'profile'`，
  每个动作在 `finally` 里 `setBusy(null)`。
- **问题**：A 动作开始 → `busy='knowledge'`；B 动作开始 → `busy='tutor'`（**覆盖**）；
  A 结束 → `setBusy(null)`（**B 还在跑，界面显示空闲**）。
  而按钮禁用是按各自动作判断的（答疑只在 `busy==='tutor'` 时禁用），
  所以解析材料期间答疑按钮**可点** —— 学生完全能踩中。
- **更危险的一层**：解析材料与补充缺口都会改 `materialVersion`，并行提交会得到一个
  说不清源头的版本号。
- **修法**：`pendingRef`（Set）+ `begin`/`end` + `isBusy(key)`；
  `begin` 在已有动作在飞时**拒绝**并说明原因。
- **⚠️ 未验证**：这是静态推演 + 类型检查的结果，**没有跑过并发场景**（无法做运行时验证）。

### R2（修正）`handleSubmit` 用 `wb.canRetry` 判断要不要清空输入框 —— 读数已过期

- **AI 原始写法**：
  ```ts
  await wb.submitMaterials([draft]);
  if (!wb.canRetry) setDraft('');
  ```
- **问题**：`wb` 是**渲染时捕获的对象**，`await` 之后读到的 `wb.canRetry` 还是提交前的值，
  与本次提交的结果无关。这个判断等于是随机的。
- **修法**：让 `submitMaterials` 返回 `boolean`，界面**成功才清空**。
  顺带把 §5.4「失败保留输入」真正落实了。
- **教训**：`await` 之后不要再读 props/闭包里的 state —— 要读结果就让调用返回结果。

### R3（修正）`startNewStudy` 的失败被记成了"读取画像失败"

- **AI 原始写法**：`rememberFailure({ kind: 'profile' }, toNotice(error, '新建会话失败。'))`。
- **问题**：`FailedAction` 里没有"新建会话"这一项，我图省事塞了 `profile`。
  后果是点「重试」会去调 `fetchProfile()` —— **动作完全不同**，
  而且此时根本没有会话，只会再报一次错。
- **修法**：新建会话失败**只提示不给重试**（按钮本来就在，再点一次即可），
  并在注释里写明"把 startNewStudy 记进可重试动作会引入自引用"。
- **教训**：`FailedAction` 是个**封闭联合**，塞不进去的语义就不该硬塞 ——
  类型系统没拦住是因为我选了欺骗性的取值，不是类型不够严。

### R4（否决）练习的失败纳入全局重试

- **AI 原始设想**：`loadQuiz` 失败也给「重试」按钮，五个动作统一。
- **否决依据**：`loadQuiz` **把题目作为返回值交给 `QuizPanel`**，
  题目列表活在面板的局部 state 里。在 hook 里重放虽然能拿到新题目，
  但**面板收不到**，页面看起来什么也没发生。
- **处置**：练习的失败走 `setNotice`（不带重试），
  由面板自己的「换一组」承担重试；并在 `FailedAction` 的注释里写明原因。
- **教训**：能重试的前提是"重放的结果能回到原来的落点"。落点不在 hook 里，就别在 hook 里重试。

## 2 被实测/自查纠正的小错

### R5（修正）`tsx` 不套用 `scripts/` 的 JSX 配置 —— `React is not defined`

- **现象**：`npm run verify:render` 报 `ReferenceError: React is not defined`。
- **原因**：`apps/web/tsconfig.json` 的 `include` 只有 `["src"]`，
  `scripts/` 不在其中，于是 tsx 对该文件没套用 `jsx: react-jsx`，走了经典 JSX 运行时。
- **AI 的第一反应（否决）**：把 `scripts` 加进 tsconfig 的 `include`。
  否决理由：那会同时把脚本纳入 `npm run build` 的 `tsc --noEmit`，
  **扩大构建的类型检查面** —— 为了修一个脚本的运行问题去改构建边界，不划算。
- **处置**：在脚本里显式 `import * as React from 'react'`，并写明原因。

### R6（修正）在 JSX 里写了 Markdown 加粗

- **AI 原始输出**：`。材料按**纯文本**参与解析 ——`（写在 TSX 的文本节点里）。
- **问题**：JSX 不是 Markdown，`**` 会原样渲染成星号显示给学生。
- **处置**：改成纯文本。写 Markdown 文档写顺手了。
- **数量**：本轮同类问题 1 处（写完顺手扫了一遍）。

## 3 本轮**未**验证的事项

1. **视觉与交互**：无浏览器（不能 `npm install -g`，没有 `agent-browser`）。
   渲染冒烟只证明"渲染不抛异常 + 关键文案在 HTML 里"。
   **布局错位、样式失效、点击无效、响应式崩掉，全部未确认。**
2. **并发修复的运行时行为**：`begin/end` 的拒绝分支从未被真正触发过。
3. **「识别可能不准」的真实链路**：服务端 `/api/parse` 的 `lowConfidence` 恒为 `[]`，
   因此该渲染路径**只在脚本构造的假数据上验证过**，真实使用中一次也不会出现 —— 要等 B5。
4. **`/api/parse` 的引入是否让真实使用变慢**：现在每条材料多一次请求。
   走 mock 时无感，**真实模型下是否值得（尤其是纯文本粘贴的场景）未评估**。
   如果形成明显延迟，可考虑加"文本直接提交"的快路径。
5. **刷新恢复路径**：依赖服务端内存会话未被回收。
6. **旧版 `verify:flow` 的 32 项与产物态的一致性**：本次只跑了开发期运行器，
   **产物形态未复跑**（B1 修复在当前分支上不存在，属于 PR #6）。
