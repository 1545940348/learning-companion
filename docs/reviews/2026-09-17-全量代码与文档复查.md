## 3 代码审查发现

### 3.1 缺陷（已登记为 `I13`–`I20`）

其中 **`I13` 是实测确认的用户可达缺陷**，不是读代码推断：

```
POST /api/session            → 201，sessionId=61554bd8-…
POST /api/tutor  {sessionId: <该 id>, materialVersion: 0, question: "单调性怎么判断"}
  ← 403 {"code":"UNAUTHORIZED_CONTENT","message":"回答未通过来源校验：AI 补充内容未经学生授权","retryable":false}

POST /api/tutor  {sessionId: null, question: "单调性怎么判断"}
  ← 200，正常返回
```

**同一个问题，走轻路径正常，走"已建会话但无材料"就 403 且不可重试。**
可达路径：点「开始新学习」或「按我的材料出题」（后者会静默建会话）之后直接提问。
这与 README「不上传材料也能提问」的核心承诺直接冲突 —— 属**真实性**问题，不只是功能缺陷。

其余各项（`I14`–`I20`）的说明与处置口径见 `todo.md`。要点：

- `I14`／`I18`：**"不静默"与"规则要接线"这两条，代码里有洞** ——
  被拒块在有块通过时无声消失；`VERIFYING_STATUSES` 声明了 `SUPPLEMENTED→VERIFIED` 的硬规则却无强制点。
- `I15`／`I16`：`/api/gap` 的两处将影响 B3 落地后的行为（conceptId 当 conceptName；幂等重放硬编码状态）。

## 4 被否决 / 被修改的真实记录

### 4.1 ✗ **我自己的一次误判：`canRetry` 的边界比较（读错，已撤回）**

初读 `apps/server/src/model/budget.ts` 时我认为 `if (budget.attempts > MAX_RETRIES) return false;`
配上 `MAX_RETRIES = 1` 会让重试**永不发生**（`attempts` 在调用前已自增到 1，`1 > 1` 为假 → 通过；
第二轮的 `2 > 1` 才拦住 —— 这其实是对的）。

**撤回依据**：`verify-error-mapping.mjs` §4.2 已断言
「★ UPSTREAM 失败后重试并成功」与「★ 共调用 2 次（1 次 + 1 次重试）」，实测通过。
**教训**：这个项目对关键路径有断言，**怀疑某个行为前先看断言有没有覆盖它**，比重新推导快且可靠。

### 4.2 ⚠️ **我改动了 `知识库.md` §11 的原文（经复核后确认该改）**

（"历史提交里仍留有那两处明文（已推送）。这是负责人已决定的'不重写历史'的代价"）。
